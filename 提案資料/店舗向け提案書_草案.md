## 1. ご提案の要旨

ヒアリングでうかがった「天候で売上が大きく変わるのに、発注の見直しがベテランの経験と勘に頼っている」という課題に対し、**天気予報・祝日や行事日・特売の予定と過去の販売実績から販売数を予測し、生鮮の発注数と惣菜の時間帯別の製造数を自動で提案するシステム**を開発しました。

今回は、このシステムの最小構成(MVP)を、**1〜2部門・短期間・費用負担なし**で試していただく「スモールスタート」をご提案します。

| | 内容 |
|---|---|
| お願いしたいこと | ① 過去の販売・在庫・廃棄データのご提供(合意した範囲のみ) ② 業務のヒアリング(1時間程度×数回) ③ 1〜2部門での試行と、利用前後のアンケート・インタビュー |
| 店舗にご用意いただくもの | 事務所PC(ブラウザ)とインターネット接続のみ |
| 費用 | 店舗のご負担はありません(研究室のAWS環境と無料の気象情報サービスで運用) |
| 既存の業務への影響 | 最終判断は担当者が行い、システムが自動で発注することはありません。既存の発注システム・PDAはそのままお使いいただけます |
| 期間(案) | 準備を含めて約3か月、うち現場での試行は2〜4週間【要調整】 |

## 2. 現状の課題(ヒアリング・インサイトワークより)

1. **天候による売上変動に、仕組みで対応できていない**
   雨天時は売上が8割程度に落ち込むなど、天候の影響が大きい一方、発注の見直しは担当者の経験と勘に依存しています。
2. **判断の重圧が特定の担当者に集中している**
   「外したら廃棄・欠品になる」という責任を担当者が一人で抱え、常態的な精神的プレッシャーになっています。
3. **情報が分断され、目視と手作業に頼っている**
   過去の実績・天気予報・特売予定などがばらばらにあり、惣菜の残量確認も目視です。現場からは「時間帯別・天気別のデータで、ワンクリックで売上予測を立てたい」という声をいただいています。
4. **廃棄ロスと機会ロス(欠品)**
   予測のずれは、そのまま廃棄や売り逃しにつながります。

研究室で比較した施策(電子棚札、ウェアラブル端末など)の中で、負担軽減・心理的負担の軽減・収益改善・導入のしやすさを総合的に評価した結果、本施策を最優先として選びました。

## 3. 解決策: AI需要予測＆発注アシスタント

### 3.1 何をするシステムか

```
過去の販売実績・在庫 ─┐
天気予報(Open-Meteo) ─┼─▶ 需要予測 ─▶ 発注数・製造数の提案 ─▶ 担当者が確認・修正・承認 ─▶ 承認済みリストを見て発注システムへ入力
祝日・行事日・特売   ─┘
```

| 部門 | 提案するもの | 担当者の作業 |
|---|---|---|
| 青果・鮮魚 | 納品日ごとの発注数(入数に合わせて切り上げ) | 画面で確認して承認(必要なら修正) |
| 惣菜 | 時間帯ごとの製造数 | 前日に承認、当日朝に陳列残数を入れて見直し |

### 3.2 特長

| 特長 | 内容 | 解決する課題 |
|---|---|---|
| **開くだけで最新の提案** | 画面を開くと提案が表示され、在庫の更新や予報の変化があれば裏で自動的に計算し直します | ワンクリックで予測したい(課題3) |
| **根拠が見える** | 天気・気温・降水、祝日・特売、前週同曜日の実績、在庫・発注残を提案と同じ行に表示します。データ不足の提案には警告を出します | 勘に頼る判断(課題1)、AIへの不安 |
| **最後は人が決める** | 提案は担当者が承認して初めて有効になります。修正もでき、修正理由を記録して予測の改善に使います | 責任の重圧(課題2)、現場の主導権 |
| **短時間で終わる** | 警告の無い提案はまとめて一括承認、承認済みの発注は印刷用の一覧で既存システムへ入力できます | 作業負担(課題3) |
| **在庫・入数まで考慮** | 在庫・未納品の発注・納品までに売れる分・入数・持越可否を踏まえた数量を出します | 廃棄・欠品(課題4) |
| **安全な運用** | ログインと部門ごとの権限、操作者の記録、HTTPS、接続元の限定。データは研究室のAWS内だけで扱います | 機密データの保護 |

### 3.3 MVP(今回お試しいただく版)の範囲

| 区分 | 含むもの | 含まないもの(将来の検討) |
|---|---|---|
| 業務 | 生鮮(青果・鮮魚)の発注提案、惣菜の時間帯別製造計画 | 値引きの判断 |
| データ | CSVでの取込(商品マスタ・POS・在庫・廃棄)、在庫・陳列残数の手入力、天気予報の自動取得、祝日・行事日・特売の登録 | 店舗システムとの自動連携 |
| 予測 | 機械学習による予測。予測モデルが使えない場合は前週同曜日の実績で代替 | 相場(市場価格)、地域イベントの反映 |
| 発注 | 承認済み発注リスト(画面・印刷) | 発注システムへの自動送信・ファイル出力 |
| 振り返り | 修正・承認の記録 | 予測と実績の比較画面(準備中) |

## 4. 期待される効果と評価方法

効果は試行で検証します。下表の目標値は研究室で置いた**仮の値**で、店舗のご意見を踏まえて確定します。

| 指標 | 測り方 | 目標値(仮) |
|---|---|---|
| 予測精度 | 過去データで、本システムの予測と「前週同曜日の実績」との誤差(WAPE)を比較。雨天日・祝日も別に集計 | 誤差を20%以上改善 |
| 発注作業時間 | 1部門・10商品の発注判断を、現行の方法と本システムで行い、所要時間を比較 | 50%削減 |
| 廃棄・欠品 | 過去データで「提案どおりに発注・製造していたら」を模擬計算し、廃棄数・欠品数を比較(原価・売価をいただければ金額換算) | 廃棄数10%削減、欠品数は増やさない |
| 心理的負担 | 利用前後のアンケート(発注への不安、提案への信頼、使いやすさ)とインタビュー | 平均1ポイント改善(5段階) |
| 提案採用率(補助) | 修正せずに承認された提案の割合 | 70%以上 |

**効果の試算イメージ(試行後に実データで記入)**

| 項目 | 試算 |
|---|---|
| 廃棄ロスの削減額(月) | 【要記入】円(= 廃棄削減数 × 原価) |
| 欠品による売り逃しの削減額(月) | 【要記入】円(= 欠品削減数 × 売価) |
| 発注作業時間の削減(月) | 【要記入】時間(= 1回あたりの短縮時間 × 回数) |

生まれた時間を、接客・売場づくり・人材育成など、人にしかできない仕事に振り向けていただくことが、本提案の最終的なねらいです。

## 6. お願いしたいデータと取り扱い

### 6.1 ご提供をお願いしたいデータ

| データ | 内容 | 期間・頻度 | 必須 |
|---|---|---|---|
| 商品マスタ | 商品コード・名称・部門・入数・リードタイム・持越の可否 | 対象商品(1部門10〜20品程度) | ○ |
| POS売上実績 | 日付・時刻(惣菜は時刻が必要)・商品・販売数 | 過去1年程度+試行中は毎日 | ○ |
| 在庫 | 数えた日時・商品・在庫数(出せない場合は画面で手入力) | 過去1年程度+試行中は発注前 | ○ |
| 廃棄実績 | 日付・商品・廃棄数 | 過去1年程度+試行中は毎日 | ○ |
| 原価・売価 | 金額換算の試算用 | ― | 任意 |

形式は研究室が定めた標準の形式(CSV)ですが、店舗のPOSから出力できる形式に合わせて、変換は研究室で行います。

### 6.2 データの取り扱い

- ご提供いただくのは、事前に合意した範囲のデータに限ります。個人情報・決済情報は扱いません。
- データは研究室のAWS環境の中だけで扱い、外部への持ち出し、ソースコードの保管場所への保存はしません。
- 接続は暗号化(HTTPS)し、接続できる場所を研究室と店舗に限定します。
- 研究成果(論文・発表)で使う場合は、店舗名・商品名を伏せるなど、公開の方法を事前にご相談します【要調整: 覚書の要否】。
- 試行終了後のデータの扱い(削除・返却)は、合意に従います。

## 8. リスクと対応

| リスク | 対応 |
|---|---|
| 予測が外れる | 必ず「前週同曜日の実績」と比べ、それより悪い予測方法は使いません。最終判断は担当者が行い、警告のある提案は一括承認できない仕組みにしています |
| AIへの不信感・慣れない | 根拠を同じ画面に表示し、修正も自由です。並行運用から始め、修正理由を予測の改善に生かします |
| 作業が増える | 毎日の作業は、データ取込(または在庫入力)と承認操作に絞りました。負担が大きい場合は試行中でも運用を見直します |
| 既存業務への影響 | 既存の発注システム・PDAには手を加えません。システムが止まっても、従来の方法で発注できます |
| データの漏えい | 6.2 の取り扱いを守り、合意した範囲のデータだけを扱います |
| システムの停止・不具合 | 計算に失敗した場合は画面に表示し、それまでの提案は残ります。研究室が対応します(対応時間【要記入】) |

## 9. ヒアリングで確認させていただきたいこと

現在は下表の「仮の前提」でシステムを作っています。実際の業務に合わせて調整します。

| 項目 | 仮の前提 |
|---|---|
| 発注を行うタイミング | 前日の閉店間際が多い |
| 発注の締め時刻 | 部門ごと(既定は閉店時刻)。仕入先ごとに違うか |
| 納品の頻度・リードタイム・納品時刻 | 毎日納品、発注の翌日、開店前に納品 |
| 持越の可否 | 青果は可、鮮魚・惣菜は不可 |
| 入数(ケース単位)と端数の扱い | 入数の倍数に切り上げ |
| 惣菜の製造計画 | 前日に作成し、当日朝に陳列残数を見て見直す |
| 惣菜の時間帯と製造開始 | 開店〜11時/11〜14時/14〜17時/17時〜閉店。製造は各時間帯の1時間前に開始 |
| 陳列残数を確認する時刻 | 製造開始の前に確認できるか |
| POSのメーカー・製品名(型番) | 未確認(出力の機能は製品によって異なる) |
| POSからのデータの出し方 | 管理画面からCSV等で出力し、研究室の変換スクリプトで取り込む(API等での自動連携は今回の範囲外) |
| POSの出力項目・時刻の細かさ・文字コード | 時刻つきで出力できる(惣菜の時間帯別の予測に必要)。文字コードは変換で対応 |
| POSの商品コードと商品マスタの対応 | JANコード等を商品コードとして使う |
| 在庫・廃棄の管理と出力 | POSとは別の管理か、同じように出力できるか |
| 在庫を数える・出力するタイミング | 発注前に出せなければ画面で入力 |
| 休業日 | 定休日・臨時休業の有無 |
| 原価・売価のご提供 | 任意(あれば金額で試算) |
| 試行の対象部門・期間 | 青果・惣菜から1〜2部門、2〜4週間 |

**POSのデータについて、ヒアリングの際にご用意いただきたいもの**

1. POSのメーカー名と製品名・型番
2. 出力ファイルの見本(数日分。値をダミーにしたもの・一部を伏せたものでも構いません)
3. 出力項目の説明書(列の意味、時刻の単位、文字コード)
4. 出力の手順(どなたが・いつ・どの画面から出力するか)

いただいた見本は研究室のAWS環境の中だけで扱い、変換スクリプトの作成と確認にのみ使います。
