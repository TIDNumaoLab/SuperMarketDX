## 詳細設計書の位置づけ

本書は、基本設計書(第3版)で定めたシステム構成を受け、AI需要予測・自動発注アシスタントの詳細設計を行うものである(作成責任者: 矢澤秀都)。予測モデルの入出力、発注数・製造数の計算式、提案の状態遷移、API・画面・テーブル・取込形式を、実装者がこの文書だけで作れる粒度で定める。仮の前提に基づく箇所は【確認事項】として示し、要件定義書「ヒアリング確認項目」の結果で確定する。

## 需要予測モデル

### モデルの種類

| モデル | 対象部門 | 予測する値 | 行の単位 |
|---|---|---|---|
| 日別モデル | 生鮮(青果・鮮魚) | 日別販売数 | 商品×日 |
| 時間帯別モデル | 惣菜 | 時間帯別販売数 | 商品×日×時間帯 |

商品ごとではなく全商品で1モデルとし、商品コードを特徴量に含める。

### 特徴量

| 列名 | 種別 | 内容 | 日別 | 時間帯別 |
|---|---|---|---|---|
| product_code | カテゴリ | 商品コード | ○ | ○ |
| day_of_week | カテゴリ | 曜日(0=月曜〜6=日曜) | ○ | ○ |
| time_band | カテゴリ | 時間帯の開始時(例: 11) | × | ○ |
| is_holiday | 真偽 | 祝日 | ○ | ○ |
| is_event_day | 真偽 | 行事日(土用の丑の日など) | ○ | ○ |
| holiday_seq | 整数 | 連休の何日目か(1始まり。連休でなければ0) | ○ | ○ |
| is_promotion | 真偽 | 対象商品の特売・チラシの期間内 | ○ | ○ |
| weather_code | カテゴリ | WMO天候コード(代表天候) | ○ | ○ |
| temperature | 数値 | 気温(℃) | ○(最高気温) | ○(時間帯の平均) |
| precipitation | 数値 | 降水確率(%)。当面は降水量(mm)を使う(下記)【確認事項】 | ○(営業時間中の最大) | ○(時間帯の最大) |
| sales_lag_7d | 数値 | 前週同曜日の販売数(時間帯別は同じ時間帯) | ○ | ○ |
| sales_avg_7d | 数値 | 基準日から遡る7日間の平均販売数(時間帯別は同じ時間帯) | ○ | ○ |

**日別の気象の集約**: 営業時間中の1時間ごとの予報(または実績)から、天候区分=降水を伴うコード(51以上)が1時間でもあればその中の最頻値、無ければ全時間の最頻値、気温=最高気温、降水確率=最大値とする。

**集約の範囲と同数の扱い**: 営業時間は「開店時 ≤ 時 < 閉店時」、時間帯は「開始時 ≤ 時 < 次の開始時」(最後の時間帯は閉店時まで)の1時間ごとの値を使う。時間帯別も天候区分は日別と同じ規則で求める。最頻値が同数のときは大きいコード(より悪い天候)を採る。

**precipitation の値**: Open-Meteo の過去実績API(archive)は降水確率を返さないため、学習と運用で列の意味を揃えるよう、当面は学習・運用とも降水量(mm)を使う(特徴量パッケージの `PRECIPITATION_SOURCE = "amount"`)。過去の降水確率が得られると分かったら降水確率に切り替えて再学習する。

**連休**: 土・日・祝日が3日以上連続する期間とする(毎週の土日だけの2日は連休としない)。

**情報の時点**: 実績系の特徴量(sales_lag_7d、sales_avg_7d)は、発注・計画作成の時点で確定しているデータだけから作る。基準日を「発注日(または計画作成日)の前日」とし、sales_avg_7d は基準日から遡る7日間の平均とする。生鮮でリードタイム1日なら、対象日の2日前が基準日になる。sales_lag_7d は対象日の7日前の実績とし、それが基準日より後になる場合は、基準日以前で最も近い同じ曜日の実績を使う。学習データもこの規則で作り、学習時と運用時の条件を揃える。

**販売実績の系列**: POS は売れた日にしか行が無いため、商品(時間帯別は商品×時間帯)の最初の販売日以降で行の無い日は販売0とみなす。最初の販売日より前は「実績なし」とする。sales_avg_7d は、7日のうち最初の販売日以降の日だけで平均する(新商品で窓の一部しか実績が無い場合)。ただし、店舗全体で POS が1行も無い日(未取込日)は販売0とみなさず「実績なし」とし、7日平均からも除く。

気象の集約の前に、時刻を日本時間にそろえてから日ごと・時間帯ごとに分ける(タイムゾーンの違う時刻が渡されても日付・時間帯がずれないように)。タイムゾーンの無い時刻は、日本時間か UTC か決められないため受け付けない。学習用の weather.csv で天候コード・気温が空欄の行は欠損として読み、その行の時間を集約から外す。

### 学習・評価・バックテスト(F-09)

1. 取込済みデータ(またはサンプルデータ)から、上の特徴量と目的変数(販売数)の表を作る。
   - 入力はサンプルデータの出力と同じ形式のフォルダ(products.csv・pos_sales.csv・weather.csv・calendar.csv・promotions.csv、あれば true_demand.csv)とし、実データも同じ形式に書き出して使う。
   - 「情報の時点」の規則を当てはめ、生鮮の計画日 = 対象日 − リードタイム、惣菜の計画日 = 対象日 − 1(前日作成)、基準日 = 計画日 − 1 とする。前週同曜日・7日平均がそろわない最初の14日は除く。
   - 店舗全体で POS が1行も無い日は未取込日とみなし、学習・評価の対象日から外す(売上0として学習しない)。
2. 候補アルゴリズムで学習する: ランダムフォレスト(scikit-learn)、勾配ブースティング(LightGBM)。
3. 時系列で分割し、直近4週間を検証期間とする。指標は WAPE(=Σ|誤差|/Σ実績)を主指標、MAE を補助とする。
4. 雨天日(代表天候が降水を伴う日)・祝日/行事日に絞った WAPE も、該当日数を併記して出す。該当日数が7日未満の場合は参考扱いとする。
   - 検証期間の予測には、本体の推論と同じ規則を当てはめる(sales_lag_7d・sales_avg_7d がともに無い行は0、天候コード・気温が欠けた行はベースライン)。評価レポートの WAPE を運用時の精度と同じ条件で出すため。
   - LightGBM は deterministic(決定的な計算)で学習し、スレッド数によって結果が変わらないようにする。
5. ベースライン(sales_lag_7d をそのまま予測値とする)と比較し、ベースラインより WAPE が悪いモデルは採用しない。
6. バックテスト: 検証期間について、「モデル予測+本書の計算式」と「ベースライン予測+同じ計算式」で日々発注・製造した場合の廃棄数・欠品数を、在庫を引き継ぎながら模擬計算して比較する。需要は、サンプルデータでは真の需要ファイルを使う。実データでは販売数を需要とみなすが、欠品時に販売数が打ち切られるため欠品数は過小評価になることを評価レポートに明記する。原価・売価がある場合は金額に換算する。
   - 生鮮は「前日閉店時の在庫を見て発注し、翌日開店時に納品する」として1日単位で模擬し、本書の計算式の発注残・販売見込は0とする(簡略化)。持越可の商品は売れ残りを翌日の在庫に、持越不可の商品は全数廃棄とする。
   - 惣菜は陳列残数0として時間帯ごとに製造し、前の時間帯の売れ残りは同じ日の次の時間帯で売れ、閉店時の残りは全数廃棄とする。
7. 採用モデルを保存し、評価レポート(版番号、学習期間、検証期間、各候補とベースラインの WAPE・MAE、条件別 WAPE と日数、バックテスト結果)を出力する。レポートには、需要の種類(真の需要か販売数か)、時間帯別の雨天の WAPE は降水を伴う時間帯で数えること、持越可の商品(青果)はバックテストの廃棄が0になることを明記する。
8. 新しい実績がたまったら再作成する(例: 週1回、手動コマンド)。

## 予測モデルのインターフェース定義

### モデルファイル

joblib で保存した辞書とし、次のキーを持つ。

| キー | 型 | 内容 |
|---|---|---|
| model | オブジェクト | `predict(features: pandas.DataFrame) -> 1次元配列` を持つ推論器(前処理を含むパイプライン) |
| meta.version | 文字列 | モデルの版番号。`{granularity}-{学習終了日 YYYY.MM.DD}-{連番}`(例: daily-2026.11.01-1) |
| meta.granularity | 文字列 | daily(日別)/ time_band(時間帯別) |
| meta.feature_columns | 文字列の配列 | 入力として期待する列名と順序 |
| meta.trained_from / meta.trained_to | 日付 | 学習期間 |
| meta.time_bands | 整数の配列または null | 時間帯別モデルで学習に使った時間帯の開始時の一覧(日別は null) |
| meta.metrics | 辞書 | 評価結果(wape、mae、baseline_wape) |

### 入力と出力

- 入力: 特徴量の表(pandas.DataFrame)。列は meta.feature_columns の通りで、日別モデルでは time_band 列を持たない。
- 出力: 行ごとの予測販売数(0以上の小数)。負の値が返った場合は本体が0に切り上げる。

### ベースラインへの切替条件

次のいずれかの場合、本体はモデルを使わずベースライン(sales_lag_7d を予測値とする。欠けている場合は sales_avg_7d)で予測し、提案に「ベースライン予測」と表示する。sales_lag_7d・sales_avg_7d がともに無い商品(新商品など)は、モデル・ベースラインのどちらでも予測値を0とし、NO_HISTORY 警告を付ける(欠損時の扱い参照)。

- 設定されたパスにモデルファイルが無い
- 適合確認に失敗した(必須キーが無い、granularity が部門と合わない、feature_columns が本体の特徴量と一致しない、試験入力での推論が失敗する、出力の行数が入力と一致しない)
- 時間帯別モデルの meta.time_bands が現在の設定の時間帯と異なる(画面に「時間帯の設定が変わったため再学習が必要です」と表示する)
- 気象データが取得できない(欠損時の扱い参照)

### 適合テスト

本体は起動時とモデルファイルの差し替え時に適合確認を行う。差し替えは、モデルファイルの更新日時・大きさ・ファイル番号(inode。Windows ではファイル ID)のいずれかが変わったことで検知し、次の予測時に読み直して適合確認する(差し替え用の API は設けない)。モデル作成用プロジェクトにも同じ確認をテストとして置き、モデルを渡す前に通過させる。

時間帯別モデルで予測するときは、現在の設定の時間帯の区切りを必ず渡す(渡さなければ予測の呼び出しを誤りとする)。区切りの確認が飛ばされないようにするため。

モデルファイルを差し替えるときは、書きかけのファイルを読み込まないよう、同じフォルダに別名でコピーしてから名前を変える。

## 提案作成処理

### きっかけ

- 自動: 担当者が発注画面・製造計画画面を開き、提案一覧API(GET /api/proposals)が呼ばれたとき
- 自動: 担当者が今日の状況を開き、GET /api/dashboard が呼ばれたとき。閲覧できる部門(店長は全部門、担当者は所属部門)ごとに、各画面の既定表示(対象日を指定しない一覧)と同じ最新性判定を行い、必要ならジョブを開始する。今日の状況はジョブの終了を待たず、進捗も取得しない。複数の部門でジョブを開始した場合は、部門ごとに別のスレッドで並行して実行する(1つずつ順に実行すると、後ろの部門のジョブが前のジョブの終了を待つ間も、実行中の判定の10分が進んでしまうため)。セッションの開始やジョブの読み込みで起きた例外(DB に接続できない等)はジョブの失敗にできないため、ログに残す。計算した提案は、その部門の画面を開いたときに一覧として表示する(実行中なら画面がそのジョブの進捗を取得する。今日の状況から部門と対象日を選んで開いた場合も、指定の計算対象をすべて含む既定表示のジョブが実行中なら、二重実行防止(下記)によりそのジョブが返る)
- 手動: 再計算ボタン(POST /api/proposals/recalculate)

一覧APIは既存の提案をすぐに返し、再計算が必要な場合はジョブを開始してジョブIDを併せて返す。画面はジョブの進捗を取得し、完了後に一覧を取り直して差し替える。

### 自動再計算の対象と判定

状態が「未承認」かつ修正ありフラグが false の提案のうち、次のいずれかに当てはまるものを再計算する。

| 条件 | 判定方法 |
|---|---|
| 未作成 | 対象商品・対象日の提案が存在しない |
| 在庫・POS・発注残の更新 | 提案の最終計算日時(proposals.calculated_at)より後に、その部門の在庫・POSの取込(import_logs)、在庫の手入力、陳列残数の入力、または提案の確定(発注残の変化)がある。取込は import_logs の終了日時、確定は提案の履歴の日時で比べる。在庫の手入力と陳列残数の入力は、行の更新日時(updated_at)で比べる(同じ基準日時で入れ直すと行が上書きされ、作成日時が変わらないため) |
| 特売・カレンダーの変更 | 提案の最終計算日時より後に、特売・カレンダーの登録・更新・削除または祝日の再取込がある。削除は行の更新日時では検出できないため、これらの操作のたびに settings の内部用キー internal.events_changed_at に日時を記録し、それと比べる |
| 設定の変更 | 提案の最終計算日時より後に、設定(安全係数・発注締め時刻・納品時刻・営業時間・惣菜の時間帯の区切り・製造開始時刻)の値が変わった。PUT /api/settings でこれらの値が実際に変わったときに settings の内部用キー internal.settings_changed_at に日時を記録し、それと比べる(再計算の判定時間だけの変更では記録しない) |
| 再計算値の採用 | 再計算値を採用して、根拠に再計算待ちの印(recalc_pending)が付いている |
| モデルの版の変更 | 提案の予測に使ったモデルの版が、現在読み込んでいるモデルの版と異なる。比べるのは計算時に読み込んでいたモデルの版(根拠の loaded_model_version)で、行ごとにベースラインで予測したかどうかではない |
| 気象予報の経過 | 提案に使った予報の取得日時から、再計算の判定時間(既定3時間)が経過している。予報が取れずに作った提案(NO_WEATHER)は予報の取得日時が無いため、最終計算日時から判定時間が経過したら再計算する(すぐに再計算すると、予報が取れない間は画面を開くたびに再計算が続くため。予報が戻れば手動再計算でも取り直せる) |

設定の変更で発注締め時刻が変わった場合、承認期限(deadline)は再計算で数量を更新する提案だけが新しい期限になる。修正あり・承認済み・承認取消後の提案は数量と同じく期限も変えない。

修正ありの提案、承認済みの提案、承認を取り消した提案は自動では数量を変えない。これらは再計算した値を proposals.recalculated_qty に保存し、画面に差分として表示する。担当者が採用(POST /api/proposals/{id}/adopt-recalculated)すると、修正前の値・修正理由を proposal_histories に残したうえで、提案値を新しい値に置き換え、状態を未承認・修正ありフラグを false に戻す。採用時は根拠を変えないため、そのままでは数量と根拠が食い違う。そこで根拠に再計算待ちの印(recalc_pending)を付け、次の最新性判定で再計算の対象とする(画面は採用後に一覧を取り直すので、すぐに数量と根拠がそろう)。

### 対象日の算出

- 生鮮: 商品ごとに「最も早い納品日」を求める。現在時刻が部門の発注締め時刻より前なら 今日+リードタイム、以後なら 今日+リードタイム+1日。発注画面の既定表示では、部門の全商品を、それぞれの最も早い納品日を対象日として1画面に並べる(リードタイムが異なる商品も漏れなく表示・計算する)。対象日を指定した場合は、その日を納品日とする提案だけを表示する。このとき計算するのは、最も早い納品日がその日以前の商品(その日に納品できる商品)とする。
- 惣菜: 製造計画画面の既定の対象日は、最初の時間帯の製造開始時刻より前なら当日、以後(ちょうどを含む)なら翌日とする。計算するのは、対象日の時間帯のうち製造開始時刻(期限)を過ぎていないものとする(過ぎた時間帯は作っても即座に期限切れになるため、新しく作らない)。前日作成(翌日以降の対象日)では全時間帯になる。一覧は対象日の時間帯の提案を、期限切れのものも含めて商品コード・時間帯の順に返す。ただし時間帯の区切りを変えた後は、現在の区切りにある時間帯の提案だけを返す(古い区切りの提案が混ざって並ばないように)。
- いずれも対象日は当日〜15日先に限る(当日は日本時間で決める)。範囲外は 400 応答とする。

### 処理の流れ

1. 最新性判定(上表)。自動の場合、対象が無ければ終了する。ジョブは計算の前に期限経過による状態更新を行って確定し、その行のロックを持ったまま気象の取得・予測をしない。手動再計算では判定を省略し、部門の全提案を再計算する(修正あり・承認済み・承認取消後の提案は、自動と同様に差分として recalculated_qty に保存する)。
2. 気象取得: 予測が必要な日(対象日。生鮮では在庫基準日から納品日の前日までの日も含む)の1時間ごとの予報を取得・保存する(同じ日の予報が再計算の判定時間内に取得済みなら再利用)。
3. 特徴量作成 → 予測(モデル、またはベースライン)。生鮮では、販売見込の計算のため、在庫基準日から納品日の前日までの各日の日別予測も行う。これらの各日の行は、すべて計画日を発注日として作り(当日・途中の日も同じ時点の情報で予測するため)、基準日は部門の POS の最新日までに抑える。学習用の表は行ごとに「対象日 − リードタイム」を計画日とするため、当日・途中の日の行とは基準日が少し異なる。
4. 発注数・製造数の計算。
5. 提案の作成・更新。予測結果を forecasts に、提案と根拠のスナップショットを proposals に保存する。

目標時間は対象20品で1分以内。

### 二重実行防止

proposal_jobs に「部門×種別×対象日」で実行中のジョブがあれば新たに開始せず、そのジョブIDを返す。種別(scope)は、生鮮の既定表示(default。target_date に発注日を記録)と対象日の指定(date。target_date に指定した納品日を記録)を分ける(同じ日付でも、発注日と納品日では計算する提案が異なるため)。ジョブの開始は部門の行をロック(FOR NO KEY UPDATE。部門を参照する行の追加は妨げない)してから登録する。実行中のまま10分を超えたジョブは失敗とみなし、新しいジョブを開始できる。失敗とみなしたジョブは、裏の処理が後で終わっても失敗のままとする(計算した提案は保存する)。ジョブの計算日時は要求を受けた時刻とし、終了日時(finished_at)は実際に終わった時刻を記録する。惣菜は既定表示も対象日の指定も1つの対象日を計算し、計算内容が同じため、いずれも種別 date・target_date に対象日を記録する(ジョブには対象日を決めてから渡し、実行中に日付が変わっても同じ日を計算する)。生鮮で対象日を指定した一覧の自動再計算では、同じ部門の既定表示のジョブが実行中で、指定の計算対象(商品×納品日)がすべてその計算対象に含まれるなら、新たに開始せずそのジョブを返す(今日の状況が始めた既定表示の計算を、印から対象日を選んで開いた発注画面でも使い、同じ提案を二重に計算しないため)。含まれない商品がある場合(リードタイムの短い商品を、最も早い納品日より後の日で表示する場合など)は、指定の対象日のジョブを開始する。手動再計算はこの扱いをしない。

### 鮮度の表示

一覧APIは次の日時を返し、画面に「予測作成 10/16 19:42、予報取得 19:40、在庫 19:30時点」の形式で表示する: 予測作成日時(表示中の提案の proposals.calculated_at の最新)、予報取得日時(weather_forecasts.fetched_at)、在庫基準日時(使用した在庫の based_at)。

## 発注数・製造数の計算

### 生鮮(日別)

```
販売見込 = 在庫基準日時から納品時刻までの予測販売数
         = 基準日の残り分(日別予測 × 残り営業時間の売上構成比)+ 途中の日の日別予測
           + 納品日の納品前の分(納品日の日別予測 × 開店から納品時刻までの売上構成比)
持越見込 = max(0, 在庫数(基準日時) + 発注残 − 販売見込)   ※持越不可の商品は0
必要数   = カバー期間の予測需要 × 安全係数(部門別、既定1.1)
発注数   = 発注単位で切り上げ( max(0, 必要数 − 持越見込) )
```

| 項目 | 定義 |
|---|---|
| 在庫数(基準日時) | その商品の、発注日(当日)を基準日時とする在庫のうち based_at が最も新しいもの。当日分が無い場合は前日以前の在庫は使わず、在庫0として NO_INVENTORY 警告を付ける |
| 発注残 | 状態「確定」の提案のうち、納品日時(納品日+部門の納品時刻)が在庫基準日時より後で、かつ納品日が対象の納品日より前のものの数量の合計。集計の前に期限経過による状態更新(提案の状態遷移参照)を行う。在庫が無い商品も、現在時刻を在庫基準日時として発注残を求め、根拠に残す(計算では在庫なしのため持越見込0) |
| 納品時刻 | 部門別の設定値(delivery_time.{部門コード}、既定=開店時刻) |
| 基準日の残り分 | 在庫基準日の日別予測 × (在庫基準時刻から閉店までの売上構成比) |
| 売上構成比 | 直近8週間の同じ曜日の時刻つきPOSから求めた、1時間ごとの売上の比率。時刻つきPOSが無い場合は営業時間の比率(残り営業時間÷営業時間)で代用。在庫基準時刻から閉店までの比率は、基準時刻の時の比率 × (60 − 分)/60 + それより後の時の比率の合計とする(開店前は1、閉店後は0) |
| 途中の日 | 在庫基準日の翌日から納品日の前日までの各日(リードタイム1日・納品は開店前の場合は無し) |
| 納品日の納品前の分 | 納品時刻が開店より後の場合に、納品日の開店から納品時刻までに売れる分。納品日の日別予測 × (1 − 納品時刻から閉店までの売上構成比)。売上構成比は納品日と同じ曜日のものを使う。納品が開店前(既定)なら0。カバー期間の予測需要は納品日1日分のままとする(納品時刻から翌日の納品時刻までの需要を、納品日1日分で近似する)。納品日が当日(リードタイム0)の場合は、販売見込を数えない |
| カバー期間 | 納品日から次回納品日の前日まで(毎日納品なら納品日1日) |
| 発注単位で切り上げ | 発注単位(入数)の倍数へ切り上げ。入数1なら整数への切り上げ |

計算例: 納品日の予測需要42.3、安全係数1.1、持越見込8、入数6 → 必要数 46.53 − 8 = 38.53 → 6の倍数に切り上げて 42。

> **【確認事項】** 納品の頻度・納品時刻、端数の丸め方(一定割合未満は切り捨て等)はヒアリングで確定する。現時点は毎日納品・開店前納品・切り上げとする。

### 惣菜(時間帯別)

```
製造数(時間帯 t) = 切り上げ( max(0, 時間帯 t の予測 × 安全係数 − 陳列残数(t)) )
陳列残数(t) = 入力時刻の直後の時間帯のみ、入力された陳列残数。それ以外の時間帯は0
             (直後の時間帯 = 開始時刻が入力時刻以後の最初の時間帯。開始時刻ちょうどの入力はその時間帯に割り当てる)
```

> **【確認事項】** この定義では、時間帯の製造開始時刻から開始時刻までの間(既定の区切りでは各時間帯の直前1時間)に入力した陳列残数は、製造開始を過ぎた時間帯に割り当てられ、どの時間帯の製造数にも反映されない。担当者が売場を確認する時刻と合うかをヒアリングで確かめ、必要なら「製造開始時刻が入力時刻以後の最初の時間帯」に割り当てる定義に改める。

- 前日作成時は陳列残数を0として全時間帯を計算する。
- 陳列残数は、対象日×商品で入力時刻が現在以前の入力のうち最も新しい1件だけを使う(同じ日に何度入力しても、最後の入力で計算する)。入力時刻は保存時のサーバーの時刻とする(端末の時計のずれで割り当て先の時間帯が変わらないように)。
- 時間帯 t の予測の入力となる販売実績は、時刻つきPOSを時間帯に集計して作る。時刻つきPOSが無い商品(日計だけの商品)は時間帯の実績が作れないため、実績なし(NO_HISTORY)とする。
- 計画日は「情報の時点」どおり 対象日 − 1(前日作成)とし、当日の再計算でも同じ基準日(計画日 − 1)で特徴量を作る(学習用の表と条件をそろえる。当日の朝に前日分の POS が取り込まれていても、当日の計画では使わない)。
- 当日に陳列残数を入力すると、製造開始時刻を過ぎていない時間帯を再計算する。承認済みの時間帯は数量を変えず、再計算値を差分として表示する。
- 前の時間帯の製造残を次の時間帯に繰り越す計算は行わない(陳列残数の入力で補正する)。

## 欠損時の扱い

既定値で黙って計算を続けることはせず、欠損ごとに次のように扱う。警告は proposals.warnings に記録し、画面で目立つように表示する。

| 欠損 | 計算方法 | 表示・承認 | 警告コード |
|---|---|---|---|
| 在庫が無い(生鮮のみ。取込も手入力も無し) | 持越見込0で計算 | 「在庫未取込」警告。一括承認の対象外、個別承認時に確認ダイアログ | NO_INVENTORY |
| 販売実績が無い(新商品など) | 予測値0 | 「販売実績なし」警告。一括承認の対象外 | NO_HISTORY |
| 気象予報が取得できない | ベースラインで予測 | 「気象データなし(ベースライン予測)」警告。一括承認の対象外。予報は取れたが対象日の天候コード・気温が欠ける場合も付け、その提案の予報取得日時は空にする | NO_WEATHER |
| 前日分のPOSが無い | 確定している最新日までで特徴量を作る | 「POS未更新」警告。前日は発注日の前日(発注日が未来の場合は当日の前日)とし、部門の POS の最新日がそれより前なら付ける。惣菜は発注日を計画日(対象日 − 1)に読み替え、特徴量の基準日(計画日の前日。計画日が未来なら当日の前日)までの POS がそろっているかで判定する | STALE_POS |
| 基準日より前に POS が1行も無い日がある(未取込日) | その日を販売0とみなさず「実績なし」として特徴量を作る(特徴量「販売実績の系列」参照)。本体では POS の取込が部門ごとのため、「部門の POS が1行も無い日」を未取込日とする(学習用の表は店舗全体のまま) | ― | ― |
| モデル未接続・不適合・時間帯区切りの不一致 | ベースラインで予測 | 「ベースライン予測」表示(警告ではない) | ― |

「在庫が無い」は、その商品の在庫が発注日(当日)を基準日時として存在しない場合とする。惣菜は前日作成時に陳列残数0で計算するのが正規の手順のため、在庫(陳列残数)の欠損による警告は付けない。

## 提案の状態遷移

| 状態 | 意味 | 遷移 |
|---|---|---|
| pending(未承認) | 作成済み。修正の有無を is_adjusted で持つ | 承認 → approved。期限経過 → expired |
| approved(承認済み) | 担当者・店長が承認 | 期限前の取消 → pending(is_adjusted を true とし、自動再計算しない)。期限経過 → confirmed |
| confirmed(確定) | 期限を過ぎた承認済み。生鮮は発注残になる | 変更不可 |
| expired(期限切れ) | 期限までに承認されなかった提案 | 変更不可(記録として残す) |

- 期限: 生鮮は部門別の発注締め時刻(対象の納品日に向けた発注日の締め時刻)、惣菜は時間帯ごとの製造開始時刻。
- 期限経過による遷移(approved → confirmed、pending → expired)は、提案を読み出す処理の冒頭で、期限を過ぎたものをまとめて更新する(定時処理は持たない)。
- 操作の API は、権限の確認 → 期限経過による状態更新の確定 → 操作 の順に行う。操作が条件違反(409・422)で拒否されても、期限経過による状態更新は残す。

| 操作 | API | 条件 | 違反時の応答 |
|---|---|---|---|
| 数量修正 | PATCH /api/proposals/{id} | pending のみ。数量は0以上の整数、修正理由は必須 | 409(状態不正)、422(入力不正) |
| 個別承認 | POST /api/proposals/{id}/approve | pending のみ。画面に表示していた数量(expected_qty)が現在の提案数と一致すること。警告付きは確認済みフラグ(confirm_warnings=true)が必要 | 409(状態不正・数量の食い違い)、422 |
| 一括承認 | POST /api/proposals/approve-bulk | 指定した提案のうち pending かつ警告なしで、表示していた数量が現在の提案数と一致するものを承認 | 除外したIDと理由を返す(エラーにしない) |
| 承認取消 | POST /api/proposals/{id}/cancel-approval | approved かつ期限前 | 409(期限切れ・状態不正。期限ちょうどを過ぎて確定した提案は「期限を過ぎているため取り消せません」) |
| 再計算値の採用 | POST /api/proposals/{id}/adopt-recalculated | pending または approved(期限前)で recalculated_qty がある | 409 |
| 他部門の操作 | 上記すべて | 担当者は自部門のみ | 403 |

修正・承認・取消・採用のたびに proposal_histories に操作・操作者・日時・前後の数量・修正理由を記録する。

承認で数量を確かめるのは、画面を開いた後に裏の再計算(他の利用者の一覧表示や判定時間の経過がきっかけ)で提案数が変わり、画面に出ていない数量を承認してしまうのを防ぐためである。食い違った場合、個別承認は 409「数量が更新されました。一覧を取り直してから承認してください」、一括承認はその提案を「数量が更新されたため一括承認から除外しました」として除外する。一括承認は提案を ID の小さい順にロックする(2人が重なる提案を同時に一括承認しても行き詰まらないように)。画面は応答を受けて一覧を取り直す。加えて、画面が再計算ジョブの実行中を知っている間は承認・一括承認のボタンを無効にする。

自動・手動の再計算で、保護された提案(修正あり・承認済み・承認取消後)の再計算値が現在の提案数と同じ場合は、recalculated_qty を空にする(差分と採用ボタンを出さない)。

### エラー応答

| ステータス | 発生条件 | メッセージ(detail) |
|---|---|---|
| 400 | 対象日が当日〜15日先の範囲外、部門と業務の組合せ不正 | 対象日は当日から15日先までを指定してください/部門と業務の組合せが正しくありません |
| 401 | 未ログイン・セッション切れ | ログインしてください |
| 403 | 権限なし(他部門の操作、担当者による店長専用操作) | この操作を行う権限がありません |
| 404 | 指定したIDの提案・特売などが存在しない | 対象が見つかりません |
| 409 | 状態不正(承認済みの修正、未承認の取消など)、期限切れ、承認時の数量の食い違い | 承認済みの提案は修正できません/期限を過ぎているため取り消せません/数量が更新されました。一覧を取り直してから承認してください 等 |
| 413 | 取込ファイルが上限(IMPORT_MAX_MB)を超える | ファイルが大きすぎます(上限 50MB)。期間を分けて取り込んでください |
| 422 | 必須項目の欠落、型の不一致、数量が0未満、未登録の商品コード、修正理由なし | 項目ごとの検証エラー |

422 の detail は、FastAPI 標準の検証エラーでは `[{loc, msg, type}]` の配列、業務上の検証では文字列とする。ただし設定 API(PUT /api/settings)の値の検証は、設定のキーごとに `[{key, msg}]` の配列で返す(画面で項目ごとにエラーを出すため)。

気象APIの失敗はAPIエラーにせず、提案側の警告(NO_WEATHER)として返す。再計算ジョブの失敗はジョブの status=failed と error で返す。error は定型文「計算中にエラーが発生しました。時間をおいて再計算してください」(10分を超えた場合は「タイムアウトしました」)とし、例外の詳しい内容はログにだけ出す。

## 画面詳細設計

### 共通

- サイドバー: 利用者の権限で表示できる画面へのリンク(先頭は今日の状況)、ログイン中の利用者名・所属部門、ログアウト。現在の画面を強調表示する。
- 日時はすべて日本時間で表示する。
- API呼び出しに失敗した場合は画面上部にエラー文言を表示し、入力内容は保持する。
- ログイン中の画面で API が 401(セッション切れ)を返したら、ログイン画面へ戻す。ログアウトは API の呼び出しに失敗してもログイン画面へ戻す。
- 業務画面の題の下に、その画面の使い方の短い説明(1文)を置いてよい(例: 在庫入力の「数えた商品だけ入力すれば保存できます。」)。
- 保存ボタンを画面下の帯に置く画面(在庫入力・設定)では、表が長くても押せるよう帯を画面下に固定する。保存の結果(「保存しました」等)は帯の中に出し、エラーがあれば帯にも「エラーがあります(画面の上に表示しています)」(設定の項目の誤りは「入力に誤りがあります(項目の横に表示しています)」)と出す(表の下の方で保存しても結果が分かるように)。

### ログイン(/login)

ログインIDとパスワードの入力、ログインボタン。失敗時は「ログインIDまたはパスワードが正しくありません。」を表示する。成功後、役割・所属部門によらず今日の状況(/dashboard)へ遷移する。店長専用の画面に担当者が来た場合や、存在しない URL も今日の状況へ戻す。

### 今日の状況(/dashboard)

ログイン後のホーム画面。サイドバーの先頭に置く。表示は画面を開いた時点の内容とし、進捗の取得や自動の取り直しは行わない(画面上部に「画面を開いた時点の内容です」と書く)。担当者には所属部門だけを表示する。

| 要素 | 仕様 |
|---|---|
| 見出し | 「今日の状況」と「MM月DD日(曜) HH:MM 現在」(応答の now) |
| 今日の締め時刻 | 横軸を時刻とした時間軸に、部門ごとに1行を置く。行の見出しは部門名と、生鮮は「発注締め」、惣菜は「今日の製造開始」とする(生鮮はリードタイムにより納品日が商品ごとに異なるため、納品日は印の読み上げ用の名前と下の一覧に出す)。deadlines のうち期限が当日のものを、期限の時刻の位置に印として置く。生鮮で期限が同じもの(リードタイムにより納品日が異なるもの)は1つの印にまとめ、件数を合計する(惣菜は時間帯ごとに1つの印とし、まとめない)。印の中は未承認の件数(0なら ✓)、印の下に「HH:MM 締め」(惣菜は「HH:MM 〇時の部」)を書く。印の状態は、期限経過で期限切れ(未承認のまま期限を過ぎた提案)あり=期限切れあり(赤の枠。印の中は「!件数」、印の下に「期限切れ N件」を添え、✓ にしない)、期限経過で期限切れなし=締め済み(灰)、未承認なし=全件承認済み(緑)、未承認あり=青、未承認ありかつ期限まで1時間以内=赤とし、赤では「あと N分」を添える。色だけに頼らず件数・✓・文字でも区別できるようにし、凡例を置く。横軸の範囲は、営業時間(応答の business_hours)の開店時と当日の最初の期限の早い方の正時から、閉店時と当日の最後の期限の遅い方の正時までとし、現在時刻の位置に縦線と「HH:MM」を引く(範囲外なら引かない)。印の文字が重なる場合は上下に振り分ける |
| 印の操作 | 印を押すと、その部門の発注画面(生鮮)または製造計画画面(惣菜)を、部門と対象日を選んだ状態で開く(納品日の異なるまとまりをまとめた印は、対象日を選ばず既定表示で開く。ただし期限切れありの印は、締め後の既定表示には期限切れの提案が出ないため、期限切れのある最も早い納品日を選んで開く。印の名前の対象は「10/17・10/18 納品分」とする)。開いた画面は、URL の部門が選べない場合と、URL の対象日が YYYY-MM-DD の形式で当日〜15日先でない場合(画面を開いたまま日付が変わった等)は、それを無視して既定の表示にする。印には「青果 10/31 納品分 発注締め15時 未承認2件 あと40分」のような読み上げ用の名前を付ける |
| 締めが近い順の未承認 | deadlines のうち未承認が1件以上で期限が現在以後のものを、期限の順に並べる。各行に期限の時刻(当日でなければ「明日」等を添える)と残り時間、部門と対象(生鮮は「MM/DD 納品分」、惣菜は「MM/DD 〇時の部」)、未承認の件数、警告の種類別件数(警告バッジ)、一括承認できる件数、その部門の画面を開くボタン(「発注を開く」「製造計画を開く」)。警告付きがあれば、一括承認できる件数に加えて「警告付きは一括承認から外れます。画面で確認してください。」と添える。該当が無ければ「締めが近い未承認はありません。」 |
| 明日の条件 | tomorrow の天気(天候の区分を文字で表示する(発注画面の根拠の表示に合わせ、アイコンは使わない)。最高/最低気温、降水量、取得時刻)、特売・チラシ(部門名・商品名・期間・内容)、祝日・行事日。予報が無ければ「予報はまだ取得していません。」(予報は提案の計算のときに取得する)、特売・行事が無ければ「なし」 |
| データの状態 | 部門ごとに、POS の最新日と取込日時、在庫の基準日時(生鮮のみ)、提案の計算状況。stale_pos が true なら警告の色で「POS未更新」、生鮮で在庫の基準日時が当日でなければ「今日の在庫が未取込です」と表示し、前回の基準日時があれば「(前回 MM/DD HH:MM)」を添える。惣菜の在庫の欄は「対象外」とする。job があれば「計算中(画面を開くと最新の結果を表示します)」、last_job が failed なら「最新の予測の計算に失敗しました: <error>」、成功していれば「MM/DD HH:MM 計算済み」(終了日時)と表示する。計算が終わっていても、この画面の件数は開いた時点の内容のままとする |
| 空状態 | 閲覧できる部門が無い場合は「表示できる部門がありません。管理者に所属部門の登録を依頼してください。」 |

### 発注(/orders)

| 要素 | 仕様 |
|---|---|
| 絞り込み | 部門(所属部門のみ。店長は全部門)、対象日(既定は未指定=各商品の最も早い納品日。表に納品日の列を表示)、状態(すべて/未承認/承認済み/確定/期限切れ) |
| 自動再計算の反映 | 再計算が終わったとき、保存していない数量の入力が無ければ一覧を差し替える。入力がある間は差し替えず、「新しい計算結果があります。」と「反映する」ボタンを出す(反映すると、提案数が変わった行の保存していない入力は新しい提案数に戻る。提案数が変わらない行の入力は残る) |
| 鮮度表示 | 「予測作成 MM/DD HH:MM、予報取得 HH:MM、在庫 HH:MM時点」。再計算中は「最新の予測を計算中… (処理済み/全体)」。進捗は2秒ごとに取得する。ジョブが失敗したら画面上部に「最新の予測の計算に失敗しました: <理由>」を表示し、既存の提案は表示したまま進捗の確認を止める。通信の失敗・5xx は取り直し、5回続けて失敗したら確認を止めてエラーを表示する。4xx(セッション切れ・ジョブが見つからない等)はすぐに止めてエラーを表示する |
| 再計算ボタン | 手動再計算。実行中は無効化 |
| 提案の表 | 1行1商品: 商品名、提案数(未承認は入力欄)、予測値(小数第1位)、天候アイコンと区分・気温・降水確率、祝日/行事日・特売のバッジ、前週同曜日の実績、在庫・発注残・持越見込、状態、警告、差分(再計算値があれば「再計算: 45(+3) 採用」) |
| 修正 | 数量を変えると、その行は承認ボタンの代わりに保存ボタンを出し、修正理由の選択(天候判断/特売・売場都合/在庫差異/その他)が必須になる(選ぶまで保存ボタンは無効)。修正理由の補足(128文字以内)は任意。保存・承認などの操作の後は一覧を取り直す |
| 承認 | 行ごとの承認ボタンと、チェックした行の一括承認ボタン。表示している提案数を併せて送る(提案の状態遷移参照)。一括承認のチェックは未承認の行だけ選べ、絞り込みの条件を変えたら選択と除外の表示を消す。一括承認で除外した行は理由(「警告があるため一括承認から除外しました」「数量が更新されたため一括承認から除外しました」等)を表示する。再計算中は承認・一括承認のボタンを無効にする |
| 承認取消 | 期限前の承認済みの行に取消ボタン |
| 警告 | 警告のある行は背景色を変え、警告文を表示。個別承認時は「在庫が取り込まれていません。このまま承認しますか?」等の確認ダイアログ |
| 期限 | 画面上部に「発注締め HH:MM まで」を表示 |
| 空状態 | 「この条件の提案はありません。」。再計算中で表示する提案が無い場合は「最新の予測を計算中です。完了すると表示します。」 |

### 製造計画(/production)

発注画面と同じ構成で、行を「商品×時間帯」とし、時間帯ごとに製造開始時刻(=承認期限)を表示する。画面上部に陳列残数の入力欄(商品ごと、入力時刻は保存時の時刻)を置き、保存すると製造開始時刻前の時間帯を再計算する。在庫・発注残・持越見込の列の代わりに陳列残数の列を表示する。

| 要素 | 仕様 |
|---|---|
| 絞り込み | 部門(惣菜の部門のみ)、対象日(既定は未指定=既定の対象日)、状態。発注締めの表示は無い |
| 対象日の表示 | 画面上部に「MM/DD の製造計画」を表示する(製造開始の列は時刻だけで、最初の時間帯の製造開始以後の既定表示は翌日の計画になるため)。日付は一覧の応答の target_date を使い、提案が0件(計算中・絞り込みの結果が空)でも表示する |
| 提案の表 | 列は 選択・時間帯(「11:00〜14:00」。最後の時間帯は閉店時刻まで)・製造開始(HH:MM)・商品・提案数・予測値・天候・祝日・特売・前週同曜日・陳列残数・状態・警告・差分・操作。入力欄の名前は「商品名 時間帯」とする(同じ商品が時間帯ごとに並ぶため) |
| 陳列残数の入力 | 入力した商品だけを、当日(日本時間)の陳列残数として送る。0以上の整数でなければ送らずに「陳列残数は0以上の整数で入力してください」と表示する。入力欄の説明に、保存した時刻の直後の時間帯から差し引くこと、各時間帯の製造開始から開始時刻までに入力した分はその時間帯の製造が始まっているため製造数に反映されないことを表示する(割り当ての【確認事項】が決まるまでの注意)。保存後は「陳列残数を保存しました(HH:MM 時点)」と表示し(時刻は応答の entered_at)、当日の計画を表示していなければ対象日を当日に切り替え、表示していれば返ったジョブの進捗を表示する(陳列残数は当日の計画にだけ効くため) |
| そのほか | 修正・承認・一括承認・承認取消・再計算値の採用・鮮度表示・自動再計算の反映・空状態は発注画面と同じ |

### 承認済み発注リスト(/orders/approved)

部門・対象日(既定は未指定=当日以降のすべて)で絞り込み、状態が承認済み・確定の提案を「商品コード順」(同じ商品は納品日順)に、商品名・納品日・発注数・発注単位・状態(承認済み/確定)・承認者を表示する(対象日が未指定のときは同じ商品が複数の納品日で並ぶため、納品日の列を置く)。該当が無ければ「承認済みの発注はありません。」と表示する。既存の発注システム・PDAへ入力しやすいよう、印刷用のレイアウト(A4縦、余計なナビゲーションを隠す)を持つ。

### データ取込(/imports)

種類(商品マスタ/POS/在庫/廃棄)と部門を選び、CSVファイルをアップロードする。結果として取込件数・スキップ件数・エラー行(行番号と理由)を表示する。取込結果は枠にまとめて常に置き、取り込む前は「取り込むと、ここに件数とスキップした行が出ます。」、スキップした行があれば「スキップした行は直して取り込み直してください。」を添える。画面に「文字コードは UTF-8、日付は YYYY-MM-DD」と書いておく(Excel で保存し直すと形式が変わりやすいため)。下部に取込履歴の一覧を表示する。商品マスタは店長のみ選択できる。

### 在庫入力(/inventory)

部門を選ぶと商品一覧が表示され、基準日時(既定は現在時刻)と商品ごとの在庫数を入力して保存する。基準日時を利用者が変えていなければ、保存の時点の現在時刻を基準日時とする(画面を開いたまま時間がたっても古い日時にならないように)。「現在時刻にする」ボタンを置き、基準日時が空なら保存しない。前回の在庫数と基準日時を併記する。保存ボタンは画面下の帯に置き、在庫数を入力した件数(「N件を入力しています」)を併せて表示する。在庫数を入力した欄は色を変える。

### 特売・チラシ(/promotions)

期間で絞り込んだ一覧と、登録フォーム(商品、開始日、終了日、内容。見出しは「特売を登録」、編集中は「特売を編集」)。行ごとに編集・削除。

### カレンダー(/calendar)

月表示で祝日・行事日を表示し、店長が日付を選んで行事日を登録・削除する。祝日は公開データから初期取込したものを表示する。土日・祝日は日付の色を変え、今日は色に加えて「今日」と書く。行事日の登録欄(見出し「行事日の登録」)は月表示の右に置く。

### 設定(/settings)

設定項目(設定項目の節)を、店舗・生鮮の発注・惣菜の製造のまとまりに分けて表示し、店長が変更・保存する。部門別の安全係数は、その部門の業務のまとまりに入れる。部門の業務は設定のキーで判定し、発注締め時刻(order_cutoff.<部門>)のある部門を生鮮とする(設定は全部門の分が返るため、担当者の閲覧できる部門だけでは判定できない)。保存ボタンは画面下の帯に置き、「変えた項目だけが保存されます。」と添える。保存では変更した項目だけを送り、製造開始時刻も変えた時間帯だけを送る。時間帯の区切りは開始時(整数)をカンマ区切りで入力し、形式が違えば送らずに画面で知らせる。変更が無ければ「変更はありません」と表示する。時間帯の区切りを変えた場合は「時間帯別モデルの再学習が必要です」と表示する。

### 予測と実績の比較(/review、Should)

部門・期間を選び、日別(惣菜は時間帯別)の予測・実績・誤差の表と、期間の WAPE、修正あり提案の割合と平均修正幅を表示する。

### proposal_histories(提案の操作履歴)/ proposal_jobs(再計算ジョブ)

## 標準取込形式

文字コード UTF-8(BOM可)、カンマ区切り、1行目は見出し行。日付は YYYY-MM-DD、日時は YYYY-MM-DD HH:MM(Asia/Tokyo)。

| 種類 | 列名 | 型 | 必須 | 例 |
|---|---|---|---|---|
| 商品マスタ(products.csv) | product_code | 文字列 | ○ | VEG-001 |
| | product_name | 文字列 | ○ | キャベツ |
| | department_code | 文字列 | ○ | VEG |
| | order_unit | 整数 | ○ | 6 |
| | lead_time_days | 整数 | ○ | 1 |
| | can_carry_over | 0/1 | ○ | 1 |
| | cost_price | 小数 | | 98 |
| | selling_price | 小数 | | 158 |
| POS売上実績(pos_sales.csv) | sales_date | 日付 | ○ | 2026-10-15 |
| | sales_time | HH:MM | | 10:23(空は日計) |
| | product_code | 文字列 | ○ | VEG-001 |
| | quantity | 整数 | ○ | 3 |
| 在庫(inventory.csv) | based_at | 日時 | ○ | 2026-10-15 19:30 |
| | product_code | 文字列 | ○ | VEG-001 |
| | quantity | 整数 | ○ | 12 |
| 廃棄実績(waste.csv) | waste_date | 日付 | ○ | 2026-10-15 |
| | product_code | 文字列 | ○ | DELI-001 |
| | quantity | 整数 | ○ | 4 |

- POS の sales_time は1時間単位に集計して保存する(sales_hour)。
- 不正な行(必須欠落、型不正、未登録の商品コード、負の数量、取込先の部門と異なる商品)はスキップし、行番号と理由を取込履歴に残す。取込全体は止めない。
- ただし、見出し行に必須列が無いファイル、UTF-8 で読めないファイル、上限(IMPORT_MAX_MB)を超えるファイルは、行単位では扱えないため取込全体を拒否する(422、上限超過は 413)。取込履歴は残さない。
- 引用符で囲んだ値の中の改行は値の一部として読み、エラーの行番号はファイル上の行番号とする。
- 見出し行に同じ列名が2つ以上あるファイル、閉じていない引用符があるファイル(残りの行が1つの値になり、黙って消えるため)は、取込全体を拒否する(422)。
- ファイル内の重複: POS・廃棄は同じ上書き単位の数量を合計し、在庫は後の行を採用する。
- POS で、同じ日・同じ商品に日計の行(sales_time が空)と時刻つきの行が混在する場合は、二重に数えないよう、その日・商品の行をすべてエラー行としてスキップする。
- 商品マスタは商品コードで更新または追加する。ファイルに無い既存商品は変更しない(取扱中のまま)。
- 再取込時の上書き単位: POS・廃棄は「日付×商品」(POSは日付×商品のすべての時刻を置き換え)、在庫は「基準日時×商品」。
- 提案は作成時点の根拠を basis に保持するため、元データの上書きは承認済み提案の根拠に影響しない。

## 外部API仕様(気象データ)

Open-Meteo を採用する。認証は不要(APIキーなし)。位置は設定の店舗緯度・経度、タイムゾーンは Asia/Tokyo を指定する。タイムアウトは10秒。

| 用途 | エンドポイント | 主なパラメータ・取得項目 |
|---|---|---|
| 予報(提案作成) | https://api.open-meteo.com/v1/forecast | start_date・end_date に対象日。hourly: temperature_2m、precipitation_probability、precipitation、weather_code |
| 過去実績(学習用) | https://archive-api.open-meteo.com/v1/archive | 期間指定。hourly: temperature_2m、precipitation、weather_code |
| 過去予報(学習用の候補) | Open-Meteo の過去予報API | 降水確率を学習に使う場合の取得元候補【確認事項】 |

- 取得結果は取得日時(fetched_at)とともに weather_forecasts / weather_actuals に保存し、根拠表示と再学習に使う。
- 予報の提供範囲(約16日先)のため、対象日は当日〜15日先に限る。
- 取得に失敗した場合(タイムアウト・範囲外・応答不正)は、提案に NO_WEATHER 警告を付けてベースラインで予測する。

> **【確認事項】** 学習用の過去気象で降水確率が得られるかを確認する。得られない場合は特徴量 precipitation を降水量(mm)とし、予測時も予報の降水量を使う。

| 同時実行 | 同じ操作がごく短い間隔で重なると、一意制約の違反で 500 になり得る箇所がある(内部用キーの初回登録、行事日の重複登録、同じ日付×商品の POS の同時取込)。研究室規模の利用では起きにくいため対策していない |
| 学習と運用の差 | 学習用の表の計画日は「対象日 − リードタイム」だが、運用で締め時刻の後に発注すると最も早い納品日は「今日 + リードタイム + 1日」になり、基準日が1日古くなる。情報の漏れではないが、学習と運用の条件が少し異なる |
