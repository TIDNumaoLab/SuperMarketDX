## 本書の位置づけ

チームメンバーが同じ手順で開発とプルリクエストのレビューを行えるよう、手元の PC に開発環境を作る手順をまとめる。
使う技術とバージョンは `技術スタック・ファイル構成.md`、チームの決まりごとはルートの `CLAUDE.md`、コマンドの細かい使い方は `app/README.md` を正とする。本書と食い違うときはそちらに合わせ、本書を改訂する。

想定する OS は Windows 10/11(Git Bash)。macOS / Linux では、本書の `.venv/Scripts/python` を `.venv/bin/python` に読み替える。

## 2. 必要なソフト

| ソフト | バージョン | 用途 | 入手先・備考 |
|---|---|---|---|
| Git for Windows | 最新 | ソース管理。Claude Code も Git Bash を使う | https://git-scm.com/ |
| GitHub CLI(`gh`) | 最新 | プルリクエストの取得・作成・レビュー | https://cli.github.com/ 。導入後 `gh auth login` |
| uv | 最新 | Python 3.11 の導入と仮想環境・ライブラリの管理 | 下記 2.1 |
| Node.js | 24 LTS | 画面(React)の開発・試験 | https://nodejs.org/ 。`npm` も付属 |
| Docker Desktop | 最新 | DB・本体・画面をまとめて起動(推奨) | https://www.docker.com/ 。Windows では WSL 2 が必要 |
| PostgreSQL 16 | 16 系 | Docker を使わない場合の DB | https://www.postgresql.org/ 。Docker を使う場合は不要 |
| エディタ | 任意 | VS Code など | — |
| libomp(macOS のみ) | 最新 | LightGBM が使う OpenMP。無いと `import lightgbm` が失敗し、モデル作成と試験が動かない | Homebrew で `brew install libomp`。Windows・Docker のイメージでは不要 |

Python は uv が 3.11 を入れるので、別に入れる必要はない(既に別の版が入っていても影響しない)。

### 2.1 すでに入っているものの確認

インストールを始める前に、すでに入っているソフトと版を確認し、足りないものだけを入れる。インストールした後も、同じコマンドで確認する。

Git Bash で次をまとめて貼り付けて実行する。入っていないソフトがあっても止まらず、全部の結果が表示される(Git が入っていない場合は Git Bash が無いので、先に Git for Windows を入れる)。

```bash
for c in "git --version" "gh --version" "gh auth status" "uv --version" "py -m uv --version" \
         "node --version" "npm --version" "docker --version" "docker compose version" \
         "psql --version" "claude --version"; do
  echo "== $c"; $c 2>&1 | head -2
done
echo "== PostgreSQL のインストール先"; ls "/c/Program Files/PostgreSQL" 2>&1
```

`command not found` と表示されたものは、入っていないか PATH が通っていない。結果を次の表で判断する。

| 確認 | 問題ない表示 | 入れる・入れ直す場合 | 見つからないときに確かめること |
|---|---|---|---|
| `git --version` | 版が表示される | 表示されない | — |
| `gh --version` | 版が表示される | 表示されない | — |
| `gh auth status` | `Logged in to github.com` | ログインしていなければ `gh auth login` を実行する | — |
| `uv --version` | 版が表示される | `uv` と `py -m uv` の両方が `command not found` / `No module named uv` | `py -m uv --version` だけ表示される場合は入っている。以降の `uv` を `py -m uv` に読み替える |
| `node --version` | `v24.` で始まる | 表示されない、または `v23` 以前・`v25` 以降 | 版が違う場合は Node.js 24 LTS を入れ直す(複数の版を使い分けるなら nvm-windows などを使う) |
| `docker compose version` | `v2.` 以降の版が表示される | 表示されない(Docker を使わない場合は不要) | Docker Desktop を起動しているか。入れる前に PowerShell で `wsl --status` を実行し、WSL 2 が使えるか確認する |
| `psql --version` | `16.` で始まる(16 以上なら可) | 15 以前しか無い、またはインストール先に `16` 以降のフォルダが無い(Docker を使う場合は不要) | インストール先(`C:\Program Files\PostgreSQL\16\bin`)があれば入っている。PATH に追加するか、フルパスで実行する |
| `claude --version` | 版が表示される | 表示されない(Claude Code を使わない場合は不要) | デスクトップアプリだけを使う場合はコマンドが無くてもよい |

PostgreSQL が入っている場合は、どのポートで動いているかも確認しておく(手順 7.2 で使う)。PowerShell で次を実行し、`postgresql-x64-16` などのサービスが `Running` かを見る。ポートは `C:\Program Files\PostgreSQL\16\data\postgresql.conf` の `port =` の行で分かる。

```powershell
Get-Service postgresql*
```

すでにこのリポジトリの環境を作ったことがある場合は、`app/` で次を実行し、`Python 3.11.x` と `ok` が表示されれば手順 4 は済んでいる(依存の更新は手順 4 の `uv pip install` をもう一度実行する)。

```bash
.venv/Scripts/python --version
.venv/Scripts/python -c "import smdx_api, smdx_features, smdx_sample, smdx_training; print('ok')"
```

### 2.2 uv のインストール

Windows(PowerShell):

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"
```

macOS / Linux:


## 3. リポジトリの取得と Git の設定

リポジトリ `TIDNumaoLab/SuperMarketDX` への招待を管理者に依頼し、承認してから取得する。

```bash

git clone https://github.com/TIDNumaoLab/SuperMarketDX.git スーパーマーケットDX
cd スーパーマーケットDX
```

コミットの作成者になる名前とメールアドレスを設定する(未設定の場合)。

```bash
git config --global user.name "GitHubのユーザー名"

```

注意:

- `.gitignore` はルート直下を一括除外し、`app/`・`設計書/`・`CLAUDE.md`・`.gitignore`・`.claude/settings.json` だけを管理対象にしている。ルート直下に作った作業用のファイルはコミットされない(新しく管理したいときは `.gitignore` に `!/<名前>` を追加する)。
- 店舗の実データ(POS・在庫・廃棄の CSV)はリポジトリ内に置かない。開発・確認にはサンプルデータ(手順 9.2)を使う。

## 4. Python 3.11 の仮想環境

仮想環境は `app/.venv` の1つを、本体・特徴量・モデル作成・サンプル生成で共用する。ライブラリのバージョンは `app/constraints.txt` で固定しているので、インストールには必ず `-c constraints.txt` を付ける(モデルファイルを本体で読み込めるようにするため)。

以下は `app/` をカレントにして実行する。

```bash
cd app
uv python install 3.11
uv venv --python 3.11 .venv
uv pip install --python .venv -c constraints.txt \
  -e "./features[dev]" -e "./backend[dev]" -e "./sample_data[dev]" -e "./model_training[dev]"
```

確認:

```bash
.venv/Scripts/python --version          # Python 3.11.x
.venv/Scripts/python -c "import smdx_api, smdx_features, smdx_sample, smdx_training; print('ok')"
```

- `constraints.txt` や各 `pyproject.toml` が更新されたプルリクエストを取り込んだら、上の `uv pip install` をもう一度実行する。
- 本体だけ触る場合は `-e "./features[dev]" -e "./backend[dev]"` だけでもよいが、レビューでは全部入れておく。

## 6. 設定ファイル(`.env`)の作成

`.env` は Git に含めない。見本の `.env.example` をコピーして作る。

```bash
cd app
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

`backend/.env` の `SESSION_SECRET` は必須(32文字以上。空のままでは本体が起動しない)。次のコマンドで作った文字列を貼り付ける。

```bash
.venv/Scripts/python -c "import secrets; print(secrets.token_urlsafe(48))"
```

- `DATABASE_URL` は手順 7 で用意する DB に合わせる(Docker Compose を使う場合は既定値のままでよい)。
- 他の項目は既定値のままでよい。項目の意味は `詳細設計書.md`「設定項目」を参照する。
- `.env` の中身・パスワードをチャットや Claude Code に貼り付けない。

## 7. DB(PostgreSQL 16)の準備

開発用の DB と、試験用の DB を分けて用意する。**試験は試験用 DB の `public` スキーマを作り直すので、開発用の DB を試験に指定しないこと。**試験用 DB の名前は `_test` で終わるものにする(それ以外の名前を指定すると、試験は DB に触れずに止まる)。

| DB 名 | 用途 |
|---|---|
| `supermarket_dx` | 開発・動作確認用(本体が使う) |
| `smdx_test` | pytest の DB 試験専用(`TEST_DATABASE_URL` で指定) |

### 7.1 Docker Compose を使う場合(推奨)

手順 9.1 で `docker compose up` すると、`supermarket_dx` を持つ PostgreSQL 16 が `localhost:5432` で起動する。試験用 DB はその中に作る。

```bash
cd app/infra
docker compose up -d db
docker compose exec db createdb -U postgres smdx_test
```

接続先は次のとおり。

```
開発用: postgresql://postgres:postgres@localhost:5432/supermarket_dx
試験用: postgresql://postgres:postgres@localhost:5432/smdx_test
```

### 7.2 Docker を使わない場合

PostgreSQL 16 を入れ、開発用と試験用の DB を作る(15 以前は `UNIQUE NULLS NOT DISTINCT` が使えないので不可)。

Windows のインストーラーは `createdb`・`psql` を PATH に追加しない。`C:\Program Files\PostgreSQL\16\bin` を環境変数 PATH に追加してターミナルを開き直すか、`"/c/Program Files/PostgreSQL/16/bin/createdb"` のようにフルパスで実行する。下の注意のとおり別のポートで動かしている場合は、`-p 5433` のようにポートも指定する。

```bash
createdb -U postgres supermarket_dx
createdb -U postgres smdx_test
```

- 既に別の版の PostgreSQL が 5432 番を使っている場合は、16 を別のポート(例: 5433)で動かし、`backend/.env` の `DATABASE_URL` と `TEST_DATABASE_URL` のポートをそれに合わせる。
- パスワードは `.env` や環境変数で渡し、コードや設計書に書かない。毎回入力したくない場合は PostgreSQL の `pgpass.conf`(Windows は `%APPDATA%\postgresql\pgpass.conf`)を使う。

開発用 DB の構造を最新にする(DB 構造の変更は必ず Alembic のマイグレーションで行う)。

```bash
cd app/backend
../.venv/Scripts/python -m alembic upgrade head
```

## 8. 試験の実行で確認

ここまでで環境ができていることを、試験がすべて通ることで確認する。気象 API(Open-Meteo)は試験では呼ばない(模擬応答を使う)ので、ネットワークが無くても通る。

`app/` をカレントにして実行する。

```bash
# 本体(DB 試験を含める)
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/smdx_test .venv/Scripts/python -m pytest backend/tests -q

# 特徴量・サンプル生成・モデル作成
.venv/Scripts/python -m pytest features/tests sample_data/tests model_training/tests -q
```

```bash
# 画面の試験と型チェック
cd frontend
npm test
npx tsc --noEmit
```

- `TEST_DATABASE_URL` を付けないと、DB を使う試験(`db` マーカー)はスキップされる。レビューでは必ず付けて、**スキップが 0 件**であることを確認する。
- PowerShell では `TEST_DATABASE_URL=... コマンド` の書き方が使えない。`$env:TEST_DATABASE_URL="postgresql://..."` を先に実行するか、Git Bash を使う。

## 9. 起動して画面で確認

### 9.1 Docker Compose で起動(推奨)

`backend/.env` を作ってから(手順 6)、`app/infra` で起動する。DB・本体・画面がまとめて起動し、DB 構造は起動時に `alembic upgrade head` で最新になる。コードを変更すると本体・画面とも自動で読み直す。

```bash
cd app/infra
docker compose up -d --build
docker compose ps
```

| 対象 | URL |
|---|---|
| 画面 | http://localhost:5173/login |
| 本体 API | http://localhost:8000(Swagger UI は `/docs`、稼働確認は `/health`) |

- ログを見る: `docker compose logs -f backend`
- 止める: `docker compose down`(データは Docker ボリューム `db-data` に残る)
- **`docker compose down -v` は DB のデータを消す。** 作り直したいとき以外は使わない。
- 依存(`constraints.txt`・`package.json`)が変わったら `--build` を付けて起動し直す。

### 9.2 Docker を使わない場合

ターミナルを2つ開く。

```bash
# 本体
cd app/backend
../.venv/Scripts/python -m alembic upgrade head
../.venv/Scripts/python -m uvicorn --factory smdx_api.main:create_app --reload --port 8000
```

```bash
# 画面
cd app/frontend
npm run dev
```

### 9.3 利用者とサンプルデータの登録

利用者を登録する画面は無いので、管理コマンドで作る(`app/backend` をカレントにして実行。Docker の場合は `docker compose exec backend python -m smdx_api.commands ...`)。`--password` は省略して入力する(シェルの履歴に残さないため)。

```bash
cd app/backend
../.venv/Scripts/python -m smdx_api.commands create_user --login-id tencho --name 店長 --role manager
../.venv/Scripts/python -m smdx_api.commands create_user --login-id tanaka --name 田中 --role staff --departments VEG,FISH
```

動作確認用のサンプルデータを作って投入する。終端日はその日の前日など、確認したい日に合わせる。

```bash
cd app
.venv/Scripts/python -m smdx_sample --out sample_data/output --end-date 2026-10-26
cd backend
../.venv/Scripts/python -m smdx_api.commands import_sample --folder ../sample_data/output
```

祝日は内閣府の「国民の祝日」CSV(`syukujitsu.csv`)を取得して `import_holidays --file syukujitsu.csv` で入れる。

### 9.4 予測モデルの作成(必要なとき)

モデルファイルは Git に含めない。モデルが無い場合、本体はベースライン(前週同曜日)で予測するので、画面の確認だけならモデルは無くてもよい。モデルを使った動作を確認するときは、サンプルデータから作って `backend/models/` に置く。

```bash
cd app
.venv/Scripts/python -m smdx_training run --data sample_data/output --granularity daily --out model_training/output
.venv/Scripts/python -m smdx_training run --data sample_data/output --granularity time_band --out model_training/output
```

評価レポート(`model_training/output/report-{版}.md`)でベースラインを上回ることを確認してから、`daily.joblib`・`time_band.joblib` を `backend/models/` にコピーする。詳細は `app/README.md`「需要予測モデルの作成と差し替え」を参照する。

Windows(PowerShell):

```powershell

```

macOS / Linux:

### 10.2 共有している設定

clone するだけで全員に同じ設定が効く。個別に設定する必要はない。

| ファイル | 内容 |
|---|---|
| `CLAUDE.md` | 起動時に自動で読み込まれる指示書。設計書を正とすること、ブランチ運用、コミットメッセージの形式など |
| `.claude/settings.json` | 実行してよいコマンドの権限(allow=確認なし / ask=毎回確認 / deny=実行しない)と、応答を日本語にする設定 |

`deny` には `master` への push、強制 push、`git reset --hard`、`rm -rf`、`.env`・鍵ファイルの読み書きなどが入っている。個人設定で `deny` のものを許可しないこと。

### 10.3 個人だけの設定

| ファイル | 用途 |
|---|---|
| `CLAUDE.local.md`(ルート直下) | 自分だけに適用したい指示 |
| `.claude/settings.local.json` | 自分だけの権限の追加(例: 自分の環境の DB ポート、`docker compose up` を確認なしにする など) |

どちらも Git に含まれない。全員に必要な設定は、`CLAUDE.md`・`.claude/settings.json` の変更をプルリクエストで提案する。

### 10.4 使うときの注意

- 店舗の実データ・`.env`・パスワード・API キーを Claude Code に読ませない・貼り付けない。
- 実装を頼むときは、設計書のどの項目(例: 詳細設計書の F-xx)を実装するかを伝える。設計書に無い判断を求められたら、勝手に決めさせず、必要なら先に設計書を改訂する。
- 提案されたコマンドは内容を読んでから許可する。出力した差分は自分で確認してからコミットする。

## 11. 開発の流れ

1. `master` を最新にして作業ブランチを切る(`master` に直接コミット・push しない)。ブランチ名は `<種別>/<内容>`(例: `feat/app-stage4-orders`)。

   ```bash
   git switch master
   git pull
   git switch -c feat/作業内容
   ```

2. 実装の前に `設計書/` の該当箇所を確認する。実装は `技術スタック・ファイル構成.md`「実装の進め方」の段階順に進め、各段階で動く状態を保つ。
3. 実装上の決まりごと(`CLAUDE.md`)を守る。特に次の点。
   - DB 構造の変更は Alembic のマイグレーションで行う(`app/backend/migrations/`)。
   - 状態を変える API は `X-Requested-With: smdx` が無い要求を 403 にする。
   - 設定値はコードに直書きしない。設定項目を増やしたら `.env.example` と詳細設計書「設定項目」も更新する。
   - 設計を変える必要が出たら、先に `設計書/` を改訂し、改訂履歴も更新する。
   - コメント・文書・コミットメッセージは日本語、識別子は英語。
4. 変更した範囲の試験を実行して通ることを確認する(手順 8)。
5. コミットする。メッセージは `<種別>: <日本語の要約>`(種別は feat / fix / docs / refactor / test / chore)。
6. push してプルリクエストを作る。説明には、何を変えたか、設計書のどこに対応するか、実行した試験とその結果を書く。

   ```bash
   git push -u origin feat/作業内容
   gh pr create --base master
   ```

前の段階のプルリクエストがまだマージされていない場合は、そのブランチから切って積み上げ、プルリクエストの説明にどの PR の上に積んでいるかを書く。

## 12. レビューの流れ

レビューする人も、手順 2〜8 の環境を用意しておく。

### 12.1 プルリクエストを手元で動かす

```bash
gh pr list
gh pr checkout <PR番号>
```

依存やマイグレーションが変わっていれば入れ直す。

```bash
cd app
uv pip install --python .venv -c constraints.txt \
  -e "./features[dev]" -e "./backend[dev]" -e "./sample_data[dev]" -e "./model_training[dev]"
cd frontend && npm ci && cd ..
cd backend && ../.venv/Scripts/python -m alembic upgrade head && cd ..
```

### 12.2 確認すること

| 観点 | 確認方法 |
|---|---|
| 試験がすべて通る | 手順 8 をすべて実行する。DB 試験を含めてスキップ 0 件であること。通過件数をレビューに書く |
| 設計書と合っている | 変更が要件定義書・詳細設計書の該当箇所と合うか。設計書に無い API・テーブル・設定の追加は、設計書が改訂されているか |
| 実装上の決まりごと | マイグレーションの有無、CSRF ヘッダの確認、設定値の直書きが無いか、`order_calc` が DB に依存していないか |
| 試験の妥当性 | 追加した機能・修正したバグに試験があるか。気象 API を実際に呼んでいないか |
| 持ち込んではいけないもの | `.env`・モデルファイル・サンプル出力・実データがコミットされていないか |
| 画面の動き | 画面の変更があれば手順 9 で起動し、実際に操作して確かめる |

`gh pr diff <PR番号>` で差分を、`gh pr view <PR番号>` で説明を確認できる。Claude Code を使う場合は、PR のブランチで `/code-review` を実行して指摘の候補を出させてもよいが、指摘は自分で確かめてから書く。

### 12.3 レビュー結果の書き方

プルリクエストのコメントに、次の形でまとめる。

1. 結論(マージしてよい / 修正後にマージ / 再レビューが必要)
2. 検証したこと(実行した試験と通過件数、手で確認したこと)
3. 良い点
4. 必須(マージ前に修正):場所(`ファイル:行`)、問題、直し方
5. できれば修正(このPRか次のPRで)
6. Minor(気づいた点)

作成者は指摘ごとに対応(修正したコミット、または対応しない理由)を返信し、レビューした人が確認してからマージする。

## 13. 困ったとき

| 症状 | 対処 |
|---|---|
| 本体が起動しない(`SESSION_SECRET` のエラー) | `backend/.env` の `SESSION_SECRET` に32文字以上の値を入れる(手順 6) |
| DB に接続できない | DB が起動しているか(`docker compose ps`)、`DATABASE_URL` のホスト・ポート・DB 名が合っているか確認する |
| 5432 番が使用中で DB コンテナが起動しない | 手元の別の PostgreSQL を止めるか、手順 7.2 のとおり別のポートを使う |
| `relation ... does not exist` | `alembic upgrade head` を実行していない。手順 7.2 の末尾を実行する |
| DB 試験がスキップされる | `TEST_DATABASE_URL` が設定されていない(手順 8) |
| `ModuleNotFoundError: smdx_...` | 手順 4 の `uv pip install` を実行していない、または `.venv` 以外の Python で実行している |
| モデルを読み込めない(版の不一致) | `-c constraints.txt` を付けずに入れた可能性がある。手順 4 をやり直し、モデルを作り直す |
| 画面からの操作が 403 になる | 画面の Axios の共通設定を通さずに要求していないか確認する(`X-Requested-With: smdx` が必要) |
| 画面が本体に接続できない | `frontend/.env` の `VITE_API_BASE_URL` と、`backend/.env` の `CORS_ALLOW_ORIGINS` を確認する |
| `claude` コマンドが見つからない | ターミナルを開き直す。それでもだめなら `claude doctor` の案内に従う |
