## 本書の位置づけ

本書は、基本設計書・詳細設計書(第3版)で定めた構成を、実装で使う技術(バージョン)とファイル・フォルダの配置に落とし込んだものである。システムプロトタイプの実装はこの構成に従って `app/` 配下に作る。モジュールの役割・API・テーブルの内容は詳細設計書を正とし、本書は「どこに何を置くか」を定める。

## 1. 技術スタック

### 1.1 バックエンド(本体)

| 項目 | 選定 | 用途・理由 |
|---|---|---|
| 言語 | Python 3.11 | 予測と本体を同じ言語で実装する。開発端末・コンテナとも 3.11 に統一する |
| Webフレームワーク | FastAPI 0.115 系 | REST API、OpenAPI(Swagger UI)の自動生成 |
| ASGIサーバ | Uvicorn | FastAPI の実行 |
| ORM | SQLAlchemy 2.0 | DBアクセス |
| マイグレーション | Alembic | DB構造の変更管理(起動時の自動作成は使わない) |
| 入出力定義 | Pydantic 2 | リクエスト・レスポンスの検証 |
| 設定 | pydantic-settings | 環境変数からの設定読込 |
| 外部API通信 | httpx | 気象データAPI(Open-Meteo)の呼び出し |
| パスワード | argon2-cffi | パスワードのハッシュ化(argon2id) |
| セッション | Starlette SessionMiddleware(itsdangerous) | 署名付きCookieによるログインセッション |
| CSV処理 | pandas 2 | 標準取込形式CSVの読込・検証 |
| モデル読込 | joblib | モデルファイルの読込 |
| テスト | pytest、httpx(テストクライアント) | 単体・結合テスト。気象APIは模擬応答 |

**CSRF対策**: セッションCookieは `SameSite=Lax`・`HttpOnly`(評価環境では `Secure` も付ける)とし、状態を変えるAPI(POST/PUT/PATCH/DELETE)には画面から独自ヘッダ `X-Requested-With: smdx` を付けさせ、無い要求は 403 で拒否する。

### 1.2 予測モデル作成・サンプルデータ生成

| 項目 | 選定 | 用途 |
|---|---|---|
| データ処理 | pandas 2、numpy | 学習用の表の作成 |
| 機械学習 | scikit-learn 1.5 系(ランダムフォレスト)、LightGBM 4 系(勾配ブースティング) | 候補アルゴリズムの学習・比較 |
| モデル保存 | joblib | モデルファイル(詳細設計書「予測モデルのインターフェース定義」の形式) |
| 試行錯誤 | Jupyter Notebook | 分析・可視化(成果物はスクリプトで再現できる形にする) |
| テスト | pytest | インターフェース適合テスト、生成データの検証 |

本体とモデル作成用プロジェクトは、同じバージョンの Python・scikit-learn・LightGBM・pandas を使う(モデルファイルを読み込めるようにするため)。バージョンは `app/` 直下の共通の制約ファイルで固定する(ファイル構成参照)。

### 1.3 フロントエンド

| 項目 | 選定 | 用途・理由 |
|---|---|---|
| 実行環境 | Node.js 24 LTS | 開発・ビルド。サポート期間内の LTS を使う(24 は 2028-04-30 まで)。20 はサポートが終了したため使わない |
| 言語/フレームワーク | React 18 + TypeScript 5 | 状態の多い承認画面を型安全に作る |
| ビルドツール | Vite 5 | 開発サーバ・ビルド |
| 画面遷移 | React Router 7 | 10画面の切り替え、権限による表示制御 |
| API通信 | Axios | 本体APIの呼び出し(Cookie送信、CSRF用ヘッダの付与を共通化) |
| スタイリング | CSS Modules | 画面数は多いが事務所PC向けの業務画面のため、ライブラリは入れない。印刷用レイアウトは `@media print` で作る |
| テスト | Vitest、React Testing Library | 計算結果の表示・警告表示・承認操作など主要な画面部品のテスト |

### 1.4 データ・インフラ

| 項目 | 選定 | 用途・理由 |
|---|---|---|
| DB | PostgreSQL 16 | 取込データ・予測・提案などの保存。`UNIQUE NULLS NOT DISTINCT` を使うため 15 以降が必須 |
| 気象データAPI | Open-Meteo(無料・APIキー不要) | 予報と過去実績の取得。過去の降水確率の取得可否は要確認(要件定義書「ヒアリング確認項目」) |
| コンテナ | Docker / Docker Compose | 開発環境と評価環境を同じ構成にする |
| 評価環境 | 研究室AWSの EC2 1台 | Docker Compose で本体・画面・DBを同じサーバーに配置する。RDS は使わない |
| HTTPS | リバースプロキシ(Caddy) | 評価環境での HTTPS 化(証明書の自動取得) |
| バージョン管理 | Git / GitHub | ソースコード管理。実データ・モデルファイル・設定値はリポジトリに含めない |
| 設計モデリング | Papyrus(Eclipse Papyrus) | システム構成・機能構成のモデル化(基本設計書参照) |

### 2.4 Git に含めないもの

`.gitignore` の一般ルール(`.env`、`__pycache__/`、`node_modules/`、`dist/` など)に加え、次は Git に含めない。

| 対象 | 理由 |
|---|---|
| `app/backend/models/*.joblib`、`app/model_training/output/` | モデルファイルは学習データに由来し、サイズも大きい |
| `app/sample_data/output/` | 生成物のため(コマンドで再生成できる) |
| 実データ(店舗のPOS・在庫・廃棄CSV) | 機密情報。研究室AWS内でのみ扱う |
| `.env`(`.env.example` のみ含める) | 接続情報・セッションの署名鍵 |

これらの除外ルールは、`app/` を作成するときに `.gitignore` へ追加する。

## 3. 実装の進め方

詳細設計書の構成に沿って、次の順に段階的に実装し、各段階で動作する状態を保つ。

1. 土台: `app/` の雛形、Docker Compose、DB とマイグレーション、ログインと権限、管理コマンド(create_user)
2. データ: サンプルデータ生成、標準取込形式の取込、祝日・特売・カレンダー、気象の取得・保存
3. 予測: 特徴量の共通パッケージ、ベースライン予測、発注数・製造数の計算(order_calc。バックテストが使うため段階4・5から前倒し)、モデル作成用プロジェクト(学習・評価・バックテスト)とモデルの接続
4. 生鮮の発注: 提案の作成・再計算・最新性判定、発注画面、承認・取消、承認済み発注リスト
5. 惣菜の製造計画: 陳列残数入力、製造計画画面
6. 評価環境: EC2 への配置と HTTPS、評価の準備

## 4. 未確定事項

技術面で残っている未確定事項は次の通り。業務面の確認事項は要件定義書「ヒアリング確認項目」を参照する。

| 項目 | 現在の方針 |
|---|---|
| 学習用の過去気象の降水確率 | Open-Meteo の過去実績API/過去予報APIで得られるかを確認。得られなければ降水量を使う |
| 予測アルゴリズムの最終選定 | 評価レポートの結果で決める |
| EC2 のインスタンス種別・アクセス元の制限方法 | 評価店舗が決まった段階で決める |
| ライブラリの細かいバージョン | 実装開始時に `constraints.txt`・`package.json` で固定する |
