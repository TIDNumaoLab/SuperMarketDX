## プロジェクト概要・背景

本プロジェクトは、小規模スーパーマーケットの社員バックオフィス業務をデジタル化し、店舗運営・人員配置の最適化を目指す『スーパーマーケットDX』プロジェクトである(東京情報デザイン専門職大学 情報デザイン学部 沼尾研究室)。

現場ヒアリングとインサイトワークにより、次の根本原因が特定された:現場のITシステムが統合されておらず、結果としてアナログな手作業と人間の目視に過度に依存している。特に天候による売上変動(雨天時に売上が8割に落ち込むなど)にシステムが対応しておらず、発注修正をベテランの「経験と勘」に依存せざるを得ない状況が、現場スタッフに常態的な精神的プレッシャーを与えている。

ソリューション比較評価(加重評価: 負担軽減×2.0、心理的解放×1.5、収益改善×1.5、導入容易性×1.0)の結果、「気象・イベント連動 AI需要予測＆自動発注アシスタント」が総合26.0ptで最優先施策として選定された(次点: ウェアラブル・ストアコントローラー24.5pt、次世代ESL 24.0pt)。本書は、この選定結果を受けて、作るべきシステム(To-Be)の要件を定義するものである。

## 目的・ゴール

**目的**: 属人的な店舗管理バックオフィス業務、特に発注業務をデジタル化によって仕組み化・効率化し、従業員の作業負担と精神的重圧を削減する。生まれた時間的余裕を、接客・販促・人材育成など付加価値の高い業務へ再配分する好循環を生み出す。

**ゴール**: これまで「経験と勘」に依存していた発注業務の属人化と精神的重圧を解消し、バックオフィス業務を徹底的に効率化する。最終的には、本システムがもたらす業務削減効果を盛り込んだ店舗への提案書を作成し、実現可能性を立証する。

**手段**: 過去のPOSデータ・在庫・気象情報・祝日/行事日・特売情報を組み合わせて需要を予測し、生鮮の発注数量と惣菜の時間帯別製造数を自動で提案し、担当者が根拠を見ながら確認・修正・承認できるアシスタントシステムを開発する。

**インサイト**: 『DXとは、現場の「人間性」と「専門性」を解放するための投資である』という解が示す通り、単なる作業短縮ではなく、「不確実性」からの解放、「分断」の解消による店舗の掌握、「人」にしかできない価値創造へのシフトをもたらすことを目指す。

## スコープ(対象範囲)

- **対象業務**: 生鮮(青果・鮮魚)の仕入発注と、惣菜の時間帯別製造計画(業務要件「部門別の業務」参照)
- **開発範囲**: データ取込(商品マスタ・POS・在庫・廃棄)、気象データの取得、祝日・行事日と特売の管理、需要予測、発注数・製造数の提案、確認・修正・承認の画面、予測モデルの学習・評価、研究用サンプルデータの生成
- **設計手法**: プロジェクト計画書の定めに従い、Papyrus(Eclipse Papyrus)を用いたモデルベースでシステム構成を設計する
- **対象外**:
  - 値引き判断
  - 次世代ESL(電子棚札)。価格表示ミス・クレームの課題はESL施策の領域であり、ソリューション評価で次点となったため対象外
  - ウェアラブル・ストアコントローラー(同じく次点のため対象外)
  - 決済情報の取り扱い
  - 既存発注システムとの直接連携(連携先確定後の将来候補 F-19)
  - 相場(市場価格)の予測への反映(データ入手が困難なため将来候補)
  - 地域イベント(将来候補 F-18)

> **【確認事項】** 対象店舗・対象部門・対象商品の最終的な範囲は、現場協力の可否(制約条件・リスク参照)に応じて確定する。

## 利用者と権限

システムの利用者は「発注担当者」(部門担当の社員)と「店長」とする。利用端末は事務所PCのブラウザのみ。利用者はログインし、操作者・承認者が記録される。発注担当者は1つ以上の部門に所属する(店長は全部門を操作できるため、所属部門は任意)。

| 操作 | 発注担当者 | 店長 |

| 数量修正・承認・承認取消 | 自部門 | 全部門 |
| 商品マスタ取込 | 不可 | 可 |
| CSV取込(POS・在庫・廃棄)・在庫の手入力・陳列残数入力 | 自部門 | 全部門 |
| 特売・チラシ登録 | 自部門 | 全部門 |
| 祝日・行事日カレンダー編集 | 不可 | 可 |
| 設定の変更 | 不可 | 可 |
| 利用者の登録 | 不可 | 不可(初期データ・管理コマンドで登録。画面は設けない) |

## 業務要件

### As-Is

天候や相場等の変動要因を踏まえた発注修正は、ベテランスタッフの経験と勘に依存している。惣菜等の残量確認は目視で行い、経験則に基づき段階的に値引きしている。PDA端末では売価変更・発注は可能だが、リアルタイムの売上把握や内線機能がなく、現場での情報アクセスが制限されている。現場からは「時間帯別、天気別などのデータを活用し、ワンクリックで売上予測を立てたい」という要望がある。

### 部門別の業務

To-Be では、部門ごとに次の業務をシステムで支援する。

| | 生鮮(青果・鮮魚) | 惣菜 |
|---|---|---|
| 業務 | 仕入発注 | 製造計画 |
| 決めるもの | 納品日の発注数量(日単位) | 対象日の時間帯別製造数 |
| 予測単位 | 日別販売数(部門から自動で決まる) | 時間帯別販売数(部門から自動で決まる) |
| 在庫の扱い | 在庫+発注残から、納品時刻までの販売見込を差し引いた持越見込を差し引く | 陳列残数を直後の時間帯から差し引く |
| 作成タイミング(仮の前提) | 発注を行うとき(ヒアリング情報では前日の閉店間際が多い) | 前日に作成し、当日朝に陳列残数・最新予報で再計算 |
| 承認期限 | 部門別の発注締め時刻 | 時間帯ごとの製造開始時刻 |

リードタイムは商品ごとに設定する(既定1日)。発注を行うタイミングに依存せず、画面を開いた時点で最新の予測に基づく提案が得られることとする。

### 業務要件一覧

| ID | 業務要件 |
|---|---|
| R-01 | 天候・イベント・曜日を反映した需要予測と発注数・製造数を、担当者が操作しなくても提示する(「ワンクリックで売上予測」の要望に対応) |
| R-02 | 提案の根拠を示し、最終判断(修正・承認)は人が行う |
| R-03 | 在庫・発注残・発注単位を考慮した数量を提案する |
| R-04 | 発注・製造計画の判断を短時間で終えられる(一括承認、1画面での確認) |
| R-05 | 予測・修正・承認の記録を残し、精度と修正傾向を振り返れる |
| R-06 | 店舗の機密データを合意した範囲で安全に扱う |

### 業務フロー

生鮮の例:

1. 担当者が(必要なら)POS・在庫のCSVを取り込むか、在庫を画面で入力する。
2. 担当者が発注画面を開く。既存の提案がすぐに表示され、最新性の判定で必要と判断されれば裏で再計算されて差し替わる。
3. 担当者は商品ごとに、提案数・予測値・根拠(天候・気温・降水確率、祝日/行事日・特売、前週同曜日の実績、在庫・発注残)と、予測の鮮度表示・警告を確認する。
4. 必要なら数量を修正し、修正理由(天候判断/特売・売場都合/在庫差異/その他)を選ぶ。
5. 個別承認、または一括承認する(警告付きの提案は一括承認の対象外)。発注締め時刻までは承認を取り消せる。
6. 承認済み発注リスト(画面・印刷)を見て、既存の発注システム・PDAへ入力する(連携先確定までの暫定運用)。

惣菜は、前日に翌日の時間帯別計画を作成・承認し、当日朝に陳列残数を入力して、製造開始時刻前の時間帯を見直す。

### イベント

- **祝日・行事日**(連休、年末年始、土用の丑の日など): 祝日は公開データ(内閣府の祝日CSV等)を初期取込し、行事日は店長が登録する。
- **特売・チラシ**: 担当者が画面から登録する(商品・期間・内容)。
- **地域イベント**: 今回は対象外とし、将来候補(F-18)とする。

## 成功基準・評価方法

目標値は仮値であり、指導教員との合意・現場ヒアリングで確定する。目標の達成判定は実データ・現場スタッフでの評価で行い、サンプルデータ・研究室メンバーでの結果は「仕組みの動作確認・操作性の参考」と位置づけて判定には使わない。

| 指標 | 測り方 | 目標値(仮) | 実データ・現場協力が無い場合 |
|---|---|---|---|
| 予測精度 | 評価レポート(F-09)。検証期間の WAPE(=Σ\|誤差\|/Σ実績) | ベースライン(前週同曜日)比で WAPE 20%以上改善。雨天日・祝日も改善(日数を併記) | サンプルで動作確認のみ(判定しない) |
| 発注作業時間 | 模擬課題(1部門・10商品の発注判断)で、現行方法(過去実績表と天気予報だけを渡して手で判断)と本システムの所要時間を計測 | 50%削減 | 研究室メンバーで実施し操作性の参考とする |
| 廃棄ロス・欠品 | バックテスト(提案通りに発注・製造した場合の廃棄数・欠品数をベースラインと比較)。原価・売価があれば金額換算(経営層向け試算) | 廃棄数10%削減、欠品数は増やさない | サンプル(真の需要あり)でシミュレーションし、参考値とする |
| 心理的負担 | 協力店舗スタッフによる利用前後アンケート(5段階: 発注への不安、提案への信頼、使いやすさ)とインタビュー | 不安・信頼が平均1ポイント改善 | 使いやすさのみ研究室メンバーで参考評価 |
| (補助)提案採用率 | 現場スタッフが修正なしで承認した提案の割合 | 70%以上 | 指標としない |

**評価スケジュール**: プロトタイプ完成後に、模擬評価・バックテスト・(協力が得られれば)特定部門・店舗でのスモールスタート評価を行い、提案書に反映する。日程はスケジュール節の再調整に合わせる。

## 制約条件

### 前提条件

| 前提条件 | 内容 |
|---|---|
| 技術環境 | 研究室のAWS環境および開発用端末が遅滞なく利用可能であること |
| 検証用データの確保 | 過去のPOSデータ(時間帯別・曜日別売上実績)・在庫データにアクセスできること。できない場合は研究用サンプルデータ(F-20)で代替し、本システムが定める標準取込形式で取り込む |
| 外部APIの利用 | 気象情報を取得する外部Web API(Open-Meteo を採用)を無料枠の範囲内で利用できること |
| 現場協力 | 店舗の発注タイミング・リードタイム・発注単位・在庫把握の方法、惣菜の製造計画の進め方についてヒアリングできること(ヒアリング確認項目参照) |

### リスク

| リスクの要因 | 内容 | 対応方針 |
|---|---|---|
| 1. 現場データの取得制限 | 店舗から機密保持の観点で詳細なPOSデータ・在庫・仕入れ履歴の提供が認められないリスク | 標準取込形式を本システム側で定め、サンプルデータ(F-20)で開発・評価できる構成とする。実データ入手時は変換スクリプトで差し替える |
| 2. 予測精度不足 | 開発期間が短く、天候やイベント連動の予測ロジックに十分な学習時間をかけられず、予測精度が安定しないリスク | 必ずベースライン(前週同曜日)と比較し、下回るモデルは採用しない。モデルを本体から切り離し、改善したモデルに差し替えられるようにする |
| 3. 現場協力不可のリスク | 実際の店舗での追加ヒアリングやプロトタイプの評価が完全に不許可となるリスク | 店舗のシステムに依存せず単独で動作する構成とする。研究室メンバーでの模擬評価を参考値として行う |
| 4. 新システムへの心理的障壁 | 現場スタッフが「経験と勘」を頼りにしていたため、AIの自動発注システムに対して不信・忌避し、定着しないリスク | 完全自動化せず人の承認を必須とし、根拠・鮮度・警告を表示し、修正理由を記録する。特定部門・店舗でのスモールスタートから始める |
| 5. スケジュール超過 | 生鮮と惣菜の両方を Must としたため、開発規模が大きくなるリスク | 生鮮の日別発注 → 惣菜の時間帯別製造計画の順に段階的に実装し、各段階で動作する状態を保つ。期限は指導教員と調整する |

## ヒアリング確認項目

設計は以下を仮の前提として進め、ヒアリング・調査の結果で確定する。

| 項目 | 仮の前提 |
|---|---|
| 発注を行うタイミング | 不定(前日の閉店間際が多いと聞いている)。タイミングに依存しない設計とする |
| 発注締め時刻 | 部門別の設定値(既定は閉店時刻)。仕入先単位で異なるかを確認 |
| 納品の頻度・リードタイム・納品時刻 | 毎日納品、リードタイム1日、納品は開店前 |
| 持越の可否 | 商品マスタで指定(鮮魚・惣菜は持越不可を既定) |
| 発注単位(ケース入数)と端数の丸め方 | 商品マスタで指定。丸めは切り上げ |
| 惣菜の製造計画の作成タイミング | 前日作成+当日朝に再計算 |
| 惣菜の時間帯の区切りと製造開始時刻 | 設定値(例: 開店〜11時、11〜14時、14〜17時、17時〜閉店。製造開始は各時間帯の1時間前) |
| 店舗POSから出力できる形式・時刻の粒度 | 標準取込形式へ変換スクリプトで対応 |
| 休業日(定休日・臨時休業)の有無と扱い | POS が1行も無い日は未取込日とみなし、予測モデルの学習から外す |
| 在庫を把握・出力できるタイミング | 発注前に出力できない場合は画面で手入力 |
| 原価・売価の提供可否 | 任意項目。無ければ数量のみで評価 |
| 学習用の過去気象で降水確率が得られるか(Open-Meteo の過去実績API/過去予報API) | 得られなければ降水量に置き換え |
| 評価指標の目標値 | 成功基準の仮値 |
| 現場評価(スモールスタート)の可否・対象部門 | 協力が得られた部門で実施 |

## 付録 試作(prototype)からの変更点

第2版は試作(prototype/)の実装内容に合わせて記述していた。第3版で To-Be 仕様に改めた主な変更点は次の通り。

| 区分 | 試作(第2版) | 第3版 |
|---|---|---|
| 予測の実行 | 手動で1件ずつ | 画面起点の自動作成・再計算(最新性判定つき)+手動再計算 |
| 業務の単位 | 全商品一律の時間帯別 | 部門別(生鮮=日別発注、惣菜=時間帯別製造計画) |
| 数量の計算 | 一律の安全係数のみ | 在庫・発注残・持越見込・陳列残数・発注単位を考慮、部門別安全係数 |
| イベント | 未対応 | 祝日・行事日、特売・チラシを特徴量に追加 |
| 予測モデル | 本体に内蔵 | モデルファイル方式で分離、ベースラインを代替として内蔵 |
| 評価指標 | 学習時のMAEのみ | WAPE・MAE、ベースライン比較、バックテスト |
| 欠損時 | 既定値で黙って続行 | 欠損ごとの計算方法と警告 |
| 提案の重複 | 同じ対象で重複作成 | 部門×商品×対象日×時間帯で1件 |
| 修正 | 修正フラグのみ | 修正理由・修正前の値を記録、自動再計算から保護 |
| 承認 | 承認のみ(取消なし) | 一括承認、承認者記録、期限までの取消、確定・期限切れ |
| 認証 | なし | ログイン、役割・所属部門による権限 |
| 天気の画面 | 週間天気・1時間天気の単独画面 | 廃止し根拠表示に統合 |
| マスタ | 固定5商品・4時間帯 | 商品マスタ取込、時間帯は設定 |
| 入力検証 | 画面のみ | サーバー側でも検証 |
| 日時の基準 | 画面の「当日」がUTC基準 | すべて Asia/Tokyo |
| サンプルデータ | 180日・5商品、需要=販売数 | 1年以上、真の需要・欠品・廃棄・在庫・特売・祝日を再現 |
| Python | Docker 3.11 / ローカル 3.9 | 3.11 に統一 |
| DB管理 | 起動時の自動作成 | Alembic のマイグレーション |
